용어를 풀면

VPC는 내 네트워크 공간, Subnet은 그 안의 작은 구역, IGW는 인터넷 연결 통로예요. Route Table은 목적지에 따라 통신을 어디로 보낼지 정하는 규칙입니다.

이번 실습

꼭 이해할 점

이름에 public을 붙이는 것만으로는 인터넷이 연결되지 않아요. IGW 연결·라우팅·퍼블릭 IP·접근 허용 설정이 함께 필요합니다.

설정 이유

웹페이지는 누구나 볼 수 있어야 해서 HTTP 80번을 전체 IPv4에 허용했어요. SSH 22번은 관리용이어서 실습 PC의 공인 IP 하나에만 허용했습니다. /32는 단일 IPv4 주소라는 뜻이에요.

기록의 범위

초기의 SSH 전체 공개 설정은 배포 전에 내 IP로 변경했어요. HTTPS·DB는 구성하지 않았으므로 443·3306·5432 등의 인바운드는 추가하지 않았습니다.
평가 때 이렇게 설명해요

“공개 기능인 HTTP 80번은 전체 IPv4에 허용하고, 관리 기능인 SSH 22번은 실습 PC의 공인 IP /32로 제한했습니다.”

1-4A 방식 수행

외부 접속 검증: A 또는 B

두 방식

A는 외부 브라우저에서 웹페이지가 표시되는지 확인하는 방식, B는 GET /health의 고정 응답으로 확인하는 방식입니다. 문서에 따르면 둘 중 하나를 선택하면 돼요.

이번 실습

A를 선택했습니다. 내 PC에서 당시 주소 http://43.203.225.25를 열어 Welcome to nginx! 페이지를 확인했고, 주소창과 페이지를 함께 캡처했어요. B의 /health는 구현하지 않았습니다.

localhost와 차이

EC2에서 localhost는 EC2 자신을, 내 PC에서 localhost는 내 PC 자신을 가리켜요. EC2 내부 200 응답만으로 외부 접속까지 증명할 수는 없습니다. 당시 서버는 이미 삭제되어 해당 IP를 현재 시연 주소로 사용할 수 없어요.
평가 때 이렇게 설명해요

“A 방식으로 외부 브라우저 접속을 검증했습니다. localhost 응답과 별도로, 퍼블릭 IP의 Nginx 페이지가 표시되는 화면을 보관했습니다.”

정리 순서

증거 보관 → EC2 종료 → EBS·EIP 확인 → VPC와 연결된 네트워크 삭제 → 키페어 삭제 → Billing 확인 순서예요. 서브넷·라우팅 테이블·보안 그룹도 정리했습니다.

근거를 구분하면

NAT Gateway·로드 밸런서·RDS의 목록이 비어 있다는 사용자 확인은 있지만, 이 세 목록의 별도 캡처는 없습니다. EIP는 “삭제했다”가 아니라 “해제 대상이 없음을 확인했다”가 정확해요.
평가 때 이렇게 설명해요

“EC2 종료 후 연결된 EBS 잔여 여부를 확인했고, EIP는 할당된 주소가 없었습니다. IGW와 VPC 등 네트워크 삭제 결과도 캡처와 ID로 확인했습니다.”

2-1구성 이유 설명

외부 요청은 어떤 경로로 서버에 도착하나요?

브라우저에 주소를 입력했을 때, 요청이 웹 서버까지 어떻게 전달되는지 말할 수 있어야 해요.

실습 기록과 답변 예시 보기 ＋

요청 흐름

외부 브라우저 → 인터넷 → IGW → Public Subnet의 EC2 → Nginx 순서로 이해하면 돼요. EC2의 보안 그룹에서 TCP 80이 허용되어야 Nginx까지 요청이 전달됩니다.

응답 흐름

Nginx가 만든 응답이 인터넷으로 돌아갈 때는 서브넷 라우팅 테이블의 기본 경로가 사용돼요. Route Table은 요청이 방문하는 서버가 아니라 경로 규칙입니다.
평가 때 이렇게 설명해요

“브라우저가 EC2의 퍼블릭 IP로 요청하면 IGW를 통해 서브넷의 EC2로 전달됩니다. 보안 그룹에서 HTTP가 허용되면 Nginx가 응답합니다.”

실습 기록과 답변 예시 보기 ＋

판단 기준

누가 어떤 기능을 써야 하는가?가 기준이에요. 웹 방문자는 HTTP 80, 관리자는 SSH 22가 필요합니다. HTTP는 전체 IPv4, SSH는 내 IP 하나로 소스를 정했어요.

평가 때 이렇게 설명해요

“공개해야 하는 웹 기능과 관리자 기능을 나누어, 필요한 인바운드 포트와 소스만 허용했습니다.”

선택한 이유

별도 애플리케이션을 개발하지 않아도 Nginx 기본 페이지로 웹 서버 배포와 외부 요청 도달을 확인할 수 있어 A를 선택했어요.

필요한 준비

서브넷의 인터넷 경로, EC2 퍼블릭 IP, 보안 그룹 HTTP 80 허용, 실행 중인 Nginx를 준비하고 외부 PC에서 확인했습니다.

검증의 한계

페이지가 표시된다는 것은 웹 요청이 도달하고 응답한다는 증거예요. DB 연결이나 애플리케이션 세부 상태까지 확인하려면 별도 상태 확인을 설계해야 합니다.
평가 때 이렇게 설명해요

“간단한 웹 배포 확인에는 Nginx 페이지로 충분해서 A를 선택했습니다. 다만 DB나 애플리케이션 내부 상태까지 검증한 것은 아닙니다.”

3-1원리 설명

Public Subnet에는 왜 기본 경로가 필요한가요?

서버에 주소가 있어도, 인터넷으로 나갈 길이 정해져 있어야 통신할 수 있어요.

실습 기록과 답변 예시 보기 ＋

경로 규칙 읽기

10.0.0.0/16 → local은 VPC 내부 목적지로 가는 경로예요. 0.0.0.0/0 → IGW는 더 구체적인 경로가 없는 IPv4 목적지를 IGW로 보내는 기본 경로입니다.

없으면 생기는 일

퍼블릭 IP가 있어도 인터넷 목적지로 보낼 경로가 없으면 통신이 성립하지 않아요. IGW 연결과 보안 그룹 설정도 함께 확인해야 합니다.

같은 값, 다른 자리

라우팅 테이블의 0.0.0.0/0은 목적지 범위, 보안 그룹 인바운드의 같은 값은 접속해 오는 소스 범위를 뜻합니다.
평가 때 이렇게 설명해요

“VPC 내부 통신은 local 경로를 사용하고, 인터넷 목적지는 IGW로 향하는 기본 경로를 사용하도록 구성했습니다.”

장애·확장·비용 대응

아직 겪지 않은 상황에 대한 대응 계획입니다. 실제 수행 결과와 구분해서 읽으세요.

4-1대응 방안 · 미실행

외부 접속이 실패하면 무엇부터 확인하나요?

요청이 어디에서 막혔는지, 인터넷 경로부터 서버 안쪽까지 순서대로 좁혀가요.

실습 기록과 답변 예시 보기 ＋

점검 순서

  1. 라우팅 — EC2 서브넷의 실제 Route Table, 기본 경로, IGW의 VPC 연결.
  2. 보안 그룹 — EC2에 연결된 SG의 80번 허용 여부. SSH라면 22번과 현재 공인 IP.
  3. 퍼블릭 IP / DNS — 현재 서버 주소와 입력한 주소가 맞는지.
  4. 서버 프로세스 / 로그 — Nginx 실행, 80번 리스닝, localhost 응답, 오류 로그.

서버에서 쓸 명령

systemctl is-active nginx
sudo ss -lntp
curl -I http://localhost
sudo nginx -t
sudo journalctl -u nginx --no-pager -n 50
sudo tail -n 50 /var/log/nginx/error.log
sudo tail -n 50 /var/log/nginx/access.log
이 명령 목록은 진단 예시이며, 해당 장애를 새로 재현해 실행한 결과가 아닙니다.

결과에 따라

localhost도 실패하면 서버 상태부터 해결해요. localhost는 정상인데 외부만 실패하면 네트워크와 주소를 다시 확인하고 필요하면 Network ACL·OS 방화벽까지 조사합니다. timeout·connection refused·HTTP 오류처럼 실패 형태도 기록해요.
평가 때 이렇게 설명해요

“라우팅, 보안 그룹, 퍼블릭 IP와 DNS, 서버 프로세스와 로그 순서로 확인하겠습니다. localhost 결과와 실패 형태를 근거로 원인 범위를 좁히겠습니다.”

4-2대응 방안 · 미실행

IAM 권한이 부족하면 어떻게 해결하나요?

관리자 권한을 바로 추가하기보다, 거부된 작업에 필요한 권한을 찾아 범위를 조정해요.

실습 기록과 답변 예시 보기 ＋

먼저 남길 정보

AccessDenied 또는 UnauthorizedOperation 오류와 함께 누가·어떤 작업을·어느 리소스에서·어느 리전에서 시도했는지 기록합니다.

정책과 대조

Action은 허용할 작업, Resource는 대상, Condition은 조건이에요. 인스턴스 종료가 거부됐다면 ec2:TerminateInstances와 대상·리전 조건부터 확인합니다. 종속 권한, 권한 경계, 조직 정책의 명시적 거부도 살펴봐요.

이번 기록의 한계

실습 사용자에는 Billing 조회 권한이 없었고 비용 확인은 루트로 수행했습니다. “IAM에 Billing 권한을 추가해 해결했다”는 실제 결과는 없습니다.
평가 때 이렇게 설명해요

“오류에서 거부된 작업과 대상·리전을 확인하고 정책의 Action·Resource·Condition을 비교하겠습니다. 필요한 범위만 조정한 뒤 같은 작업으로 재검증하겠습니다.”

4-3확장 설계 · 미배포

트래픽이 늘어 EC2를 2대로 늘린다면?

서버를 한 대 더 만드는 것뿐 아니라, 요청을 나누고 장애와 데이터 공유도 고려해야 해요.

실습 기록과 답변 예시 보기 ＋

현재 구조

단일 t3.micro와 단일 가용 영역이어서 한 서버에 요청이 집중됩니다. 실제 부하 측정은 하지 않았으므로 CPU·메모리·네트워크 중 병목을 확정할 수는 없어요. 응답 시간, 요청량, 자원 사용량, 로그부터 측정합니다.

확장 설계

외부 사용자 → ALB → Target Group의 EC2 두 대로 요청을 나눕니다. ALB는 요청 분산을 담당하고 상태 확인으로 정상 서버에 전달해요. 일반적인 리전 ALB를 위해 서로 다른 가용 영역의 서브넷 두 개 이상을 준비하고, EC2도 가용 영역 분산을 검토합니다.

함께 바꿀 것

외부 접속은 ALB DNS 이름을 사용하고, 서버 HTTP의 소스는 ALB 보안 그룹으로 제한합니다. 세션·파일은 서버끼리 자동 공유되지 않으므로 공용 저장소 등을 별도 설계해요. 자동 증감이 필요하면 Auto Scaling을 검토합니다.

수행 여부

ALB, 두 번째 EC2, 추가 서브넷, Auto Scaling은 이번 실습에서 배포하지 않았습니다.
평가 때 이렇게 설명해요

“먼저 부하 지표로 병목을 확인하겠습니다. 확장이 필요하면 ALB와 Target Group으로 두 EC2에 요청을 분산하고 가용 영역, 보안 그룹, 세션과 파일 공유도 함께 설계하겠습니다.”

4-4대응 방안 · 금액 한계 있음

실습 기록과 답변 예시 보기 ＋

분석 순서

청구서와 Cost Explorer에서 기간 → 서비스 → 리전 → 사용 유형으로 좁힙니다. 예상 비용, 발생한 사용 비용, 크레딧 적용 후 금액을 구분하고 반영 지연도 고려해요.

확인할 자원

EC2, 종료 후 남은 EBS, 별도 할당 EIP와 퍼블릭 IPv4 사용부터 확인해요. 비용 내역에 따라 NAT Gateway·로드 밸런서·RDS·스냅샷·데이터 전송도 봅니다. 실습 이름·ID·리전 등으로 대상을 확인하고 필요한 데이터를 보관한 뒤 해당 자원을 정리합니다.
