### 1. 과제 목적과 실행 환경 소개

**설명:** “리눅스에서 앱을 안전하게 실행하고, 상태와 시스템 자원을 매분 점검해 로그로 기록하는 과제입니다. 로그 크기와 개수도 관리합니다. 보너스는 제외했습니다.”

터미널 B에서 확인합니다.

```bash
cat /etc/os-release
uname -r
ps -p 1 -o comm=
```

**보여 줄 것:** Ubuntu 22.04, WSL2 커널, PID 1의 systemd. Docker 컨테이너를 만든 것이 아니라 WSL Ubuntu에 SSH·UFW·cron과 앱을 설치해 실행한 환경이라고 설명합니다.

#### 명령어를 이해하고 설명하기

| 명령 | 확인하는 내용 | 평가 때 짚을 출력 |
|---|---|---|
| `cat /etc/os-release` | 설치된 리눅스 배포판과 버전 | Ubuntu 22.04.5 LTS |
| `uname -r` | 리눅스 커널 버전 | microsoft-standard-WSL2 포함 |
| `ps -p 1 -o comm=` | PID 1 프로세스의 이름 | systemd |

`cat`은 파일 내용을 읽습니다. `/etc/os-release`는 배포판 정보 파일입니다. `ps`는 프로세스 정보를 보여 주며, `-p 1`은 1번 프로세스만 선택하고 `-o comm=`은 이름 열을 머리글 없이 출력합니다. systemd는 여기서 SSH와 cron 같은 서비스를 관리하는 역할을 합니다.

```text
Windows 컴퓨터
└─ WSL2 Ubuntu
   ├─ sshd: 원격 접속을 받음, TCP 20022
   ├─ 과제 앱: 서비스 연결을 받음, TCP 15034
   ├─ UFW: 들어오는 연결 허용·차단
   ├─ monitor.sh: 상태·자원 점검, 로그 기록·순환
   └─ cron: monitor.sh를 매분 실행
```

**발표 예시:** “Windows 안의 WSL2 Ubuntu에서 실습했습니다. 컨테이너를 만든 것이 아니라 Ubuntu에 서비스를 직접 설치했습니다. 앱은 터미널 A에서 유지하고, 터미널 B에서 설정과 모니터링 결과를 보여 드리겠습니다.”

**추가 질문: PowerShell에서 `wsl`로 들어가는 것이 SSH인가요?** 로컬 WSL Ubuntu를 여는 동작입니다. SSH는 접속 대상의 SSH 서버에 인증하고 연결하는 별도 방법입니다.

### 2. SSH 설정 확인 — 평가 1-1, 3-1

**설명:** “SSH는 암호화된 원격 접속 방법입니다. 접속 포트를 20022로 바꾸고 Root 직접 로그인을 차단했습니다.”

```bash
sudo /usr/sbin/sshd -t && echo "SSH 설정 문법 정상"
sudo /usr/sbin/sshd -T | grep -E '^(port|permitrootlogin) '
sudo ss -ltnp | grep sshd
```

**보여 줄 것:** `port 20022`, `permitrootlogin no`, 실제 20022 LISTEN. `sshd -T`는 해석된 설정이고 `ss`는 실행 중인 소켓 확인입니다.

**이유 설명:** 포트 변경은 기본 포트 대상의 단순 자동 접속 시도를 줄이는 보조 조치입니다. Root 직접 접속은 탈취 시 바로 최고 권한을 주므로 막고, 일반 계정에서 필요한 작업에만 sudo를 사용합니다. 변경 방법을 질문받으면 수행 내역서 **3.3절**을 설명합니다.

#### 설정 파일과 명령어의 차이

SSH는 Secure Shell의 약자로, 다른 컴퓨터에 암호화된 연결로 접속해 명령을 실행하는 방법입니다. `ssh`는 접속하는 클라이언트이고, `sshd`는 연결을 받는 서버 프로그램입니다.

| 명령·설정 | 의미 |
|---|---|
| `sudo` | 해당 명령을 관리자 권한으로 실행 |
| `sshd -t` | 설정 문법과 필요한 기본 조건 검사 |
| `sshd -T` | 설정 파일을 해석한 적용 예정 값 출력 |
| `grep -E` | 정규식으로 필요한 줄만 선택 |
| `ss -ltnp` | TCP LISTEN 소켓과 소유 프로세스 확인 |
| `Port 20022` | 접속을 받을 SSH 포트 지정 |
| `PermitRootLogin no` | Root 계정의 직접 SSH 로그인 금지 |

정상 출력에서 다음을 설명합니다.

```text
port 20022
permitrootlogin no
LISTEN ... 0.0.0.0:20022 ... users:(("sshd",pid=...))
LISTEN ... [::]:20022 ... users:(("sshd",pid=...))
```

`0.0.0.0`은 리눅스의 모든 IPv4 인터페이스에서 연결을 받는 주소이고, `[::]`는 IPv6의 대응 주소입니다. LISTEN은 연결을 기다리는 상태입니다. 이것만으로 Windows 방화벽이나 WSL 네트워크를 통과한 외부 접속까지 확인된 것은 아닙니다.

#### 어디서 변경하고 어떻게 반영하는가?

```bash
sudo nano /etc/ssh/sshd_config
```

전역 설정 영역에서 활성화된 설정을 다음처럼 수정합니다.

```text
Port 20022
PermitRootLogin no
```

줄 앞의 `#`는 주석입니다. nano에서는 `Ctrl+O` → Enter로 저장하고 `Ctrl+X`로 나옵니다. `/etc/ssh/sshd_config.d/*.conf`의 추가 설정도 읽히므로 중복과 우선순위를 확인해야 합니다. `Port`는 여러 값을 지정할 수 있어서 기존 22번 설정이 활성 상태로 남아 있지 않은지도 확인합니다. 첫 `Match` 앞의 전역 영역에 설정합니다. [Ubuntu 22.04 SSH 설정 매뉴얼](https://manpages.ubuntu.com/manpages/jammy/man5/sshd_config.5.html).

새 포트를 방화벽에서 허용하고 문법 검사에 성공한 뒤 재시작합니다.

```bash
sudo ufw allow 20022/tcp
sudo /usr/sbin/sshd -t && sudo systemctl restart ssh
sudo /usr/sbin/sshd -T | grep -E '^(port|permitrootlogin) '
sudo ss -ltnp | grep sshd
```

`&&`는 왼쪽 명령이 성공할 때만 오른쪽 명령을 실행합니다. 파일에 설정을 쓴 것, 설정이 해석되는 것, 실행 중인 서비스가 그 포트에서 기다리는 것은 각각 확인할 대상입니다. 백업과 새 접속 확인을 포함한 전체 변경 절차는 수행 내역서 **3.3절**을 사용합니다.

**추가 질문: `PermitRootLogin yes`면 바로 Root를 빼앗기나요?** Root 원격 로그인을 허용하지만 인증을 없애지는 않습니다. Root 비밀번호나 허용된 개인 키 등으로 인증에 성공해야 접속합니다. 인증 정보가 탈취되면 곧바로 최고 권한으로 진입할 수 있어 직접 접속을 제한했습니다. 일반 계정도 sudo 권한이 탈취되면 위험하므로 `no` 하나로 모든 계정 공격을 막는 것은 아닙니다.

**추가 질문: 포트만 바꾸면 안전한가요?** 변경한 포트도 찾을 수 있으므로 보조 조치입니다. 이번 과제에서는 Root 접속 제한과 방화벽·권한 정책을 함께 적용했습니다.

<a id="step-3"></a>

### 3. 방화벽 확인 — 평가 1-2

```bash
sudo ufw status verbose
```

출력에서 다음 세 가지를 순서대로 짚습니다.

1. `Status: active`: 방화벽 활성화.
2. `deny (incoming)`: 들어오는 연결을 기본 차단.
3. 20022/tcp와 15034/tcp의 `ALLOW IN`: SSH와 앱에 필요한 포트만 허용.

**설명:** “IPv6의 `(v6)` 규칙도 같은 두 포트를 허용합니다. 방화벽 허용은 연결 정책이고, 앱이 포트를 실제로 열었는지는 뒤에서 ss로 확인합니다.”

#### 출력 전체를 읽는 방법

```text
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), deny (routed)

20022/tcp       ALLOW IN    Anywhere
15034/tcp       ALLOW IN    Anywhere
20022/tcp (v6)  ALLOW IN    Anywhere (v6)
15034/tcp (v6)  ALLOW IN    Anywhere (v6)
```

| 표시 | 설명 |
|---|---|
| `active` | UFW 방화벽이 활성 상태 |
| `deny (incoming)` | 들어오는 연결은 기본 차단 |
| `allow (outgoing)` | 리눅스에서 나가는 연결은 기본 허용 |
| `deny (routed)` | 이 리눅스를 통과해 다른 대상으로 전달하는 트래픽의 기본 차단 정책 |
| `ALLOW IN` | 해당 포트의 들어오는 연결 허용 |
| `Anywhere` | 출발지 IP를 특정 주소로 제한하지 않음 |
| `(v6)` | IPv6 규칙이며 추가 포트라는 뜻은 아님 |

**발표 예시:** “활성화 여부는 active로 확인하고, 기본 수신 정책은 deny입니다. 아래 예외 규칙에는 TCP 20022와 15034만 있습니다. 20022는 관리자 SSH 접속, 15034는 과제 앱용입니다.”

#### 포트 허용과 서비스 동작을 구분하기

| 방화벽 정책 | 앱의 LISTEN | 해석 |
|---|---|---|
| 허용 | 있음 | 앱이 연결을 받을 준비가 되어 있음. 외부 접속 경로는 별도 확인 |
| 허용 | 없음 | 방화벽만 열었고 연결을 받아 줄 앱은 없음 |
| 차단 | 있음 | 앱은 준비됐지만 해당 외부 연결이 방화벽에서 차단될 수 있음 |

**추가 질문: 방화벽을 변경하는 명령은?** `sudo ufw allow 20022/tcp`처럼 허용 규칙을 추가합니다. 기본 정책 변경·불필요한 기존 규칙 정리는 현재 규칙을 먼저 확인한 뒤 수행합니다. 평가 중에는 이미 정상인 설정을 반복 변경하지 않고 `status verbose`로 보여 줍니다.

**캡처 범위:** 명령어부터 active, 기본 정책, 두 포트의 IPv4·IPv6 규칙까지 한 화면에 포함합니다. 기존 증거는 [UFW 확인 캡처](captures/01-firewall.png)입니다.

### 4. 계정·그룹과 접근 권한 확인 — 평가 1-3, 2-3, 3-2

```bash
id agent-admin
id agent-dev
id agent-test
getent group agent-common agent-core
sudo ls -ld /home/agent-admin/agent-app \
  /home/agent-admin/agent-app/upload_files \
  /home/agent-admin/agent-app/api_keys \
  /var/log/agent-app
sudo ls -l /home/agent-admin/agent-app/bin/monitor.sh
```

**설명:** “common에는 세 계정이 모두 있고, core에는 admin과 dev만 있습니다. test는 공용 업로드 영역을 사용하지만 키와 로그에는 접근할 수 없습니다. 스크립트 소유자는 dev이고, admin은 core 그룹의 실행 권한으로 모니터와 cron을 실행합니다.”

**보여 줄 것:** 운영 monitor.sh의 소유자 agent-dev, 그룹 agent-core, 권한 750. 소유자는 수정 가능하고 그룹은 읽기·실행만 가능합니다. 제출 복사본의 권한과 구분합니다.

**실제 접근 증거:** 수행 내역서 **4절**의 계정별 접근 검사 결과를 함께 보여 줍니다. 그룹 구성만 보여 주는 것으로 실제 접근 검사를 대신하지 않습니다. 키의 실제 내용은 출력할 필요가 없습니다.

#### 계정과 권한 출력 읽기

`id`의 uid는 사용자 번호, gid는 기본 그룹 번호, groups는 소속 그룹 목록입니다. `getent group`은 해당 그룹과 구성원을 조회합니다.

| 계정 | 공용 그룹 common | 운영 그룹 core | 실제 디렉토리 접근 결과 |
|---|---|---|---|
| agent-admin | 포함 | 포함 | 업로드·키·로그 모두 rwx |
| agent-dev | 포함 | 포함 | 업로드·키·로그 모두 rwx |
| agent-test | 포함 | 미포함 | 업로드 rwx, 키·로그 접근 불가 |

`ls -l`은 파일의 상세 정보를, `ls -ld`는 디렉토리 안의 목록 대신 디렉토리 자체의 권한을 보여 줍니다. 운영 스크립트의 출력은 다음 구조입니다.

```text
-rwxr-x--- 1 agent-dev agent-core ... monitor.sh
```

```text
- | rwx | r-x | ---
    소유자  그룹  그 외
```

`r=4`, `w=2`, `x=1`로 합산하므로 rwx는 7, r-x는 5, ---는 0입니다. 그래서 이 권한을 750이라고 부릅니다.

| 권한 | 일반 파일에서 | 디렉토리에서 |
|---|---|---|
| r | 내용 읽기 | 안의 이름 목록 읽기 |
| w | 내용 변경 | 파일 생성·삭제·이름 변경. 일반적으로 x도 필요 |
| x | 프로그램으로 실행 | 경로 통과와 안의 항목 접근 |

#### ACL과 setgid가 필요한 이유

```bash
sudo getfacl -p /home/agent-admin \
  /home/agent-admin/agent-app/upload_files \
  /home/agent-admin/agent-app/api_keys \
  /var/log/agent-app
```

ACL은 기본 소유자·그룹·기타 권한 외에 특정 사용자나 그룹의 권한을 지정하는 방법입니다. `ls`의 `+` 표시는 추가 ACL이 있음을 나타냅니다. 홈 디렉토리의 `group:agent-common:--x`는 필요한 하위 경로까지 통과하게 하지만 홈 목록 전체를 읽게 하지는 않습니다.

디렉토리 그룹 실행 자리의 `s`는 setgid입니다. 이 디렉토리에 새 파일을 만들 때 디렉토리 그룹을 이어받도록 돕습니다. `default:` ACL은 새로 생성되는 항목에 적용되는 기본 권한이고, `mask`는 그룹 계열 ACL의 유효 권한 상한입니다. 최종 접근은 상위 경로와 대상 권한을 함께 확인해야 합니다.

#### 실제 계정으로 접근 확인하기

다음 예시는 읽기·쓰기·경로 통과가 모두 가능한지 검사합니다. 파일을 만들거나 키 내용을 읽지는 않습니다.

```bash
sudo -u agent-test /bin/bash -c \
  'test -r "$1" && test -w "$1" && test -x "$1"' \
  bash /home/agent-admin/agent-app/upload_files
echo "test 업로드 rwx 검사: $?"

sudo -u agent-test test -x /home/agent-admin/agent-app/api_keys
echo "test 키 경로 접근 검사: $?"
```

예상값은 업로드 검사 0, 키 접근 검사 1입니다. 이때 1은 접근 차단을 확인한 정상적인 시험 결과입니다. 계정별 9개 전체 결과는 수행 내역서 4절에서 확인합니다.

**추가 질문: 왜 test에게 키와 로그 접근을 막았나요?** 업로드 테스트 업무에 필요하지 않은 권한이기 때문입니다. 키 유출과 로그 정보 노출·변조를 제한하는 최소 권한 원칙입니다.

### 5. 앱 시작과 서비스 포트 확인 — 평가 1-4

앱이 이미 실행 중이면 두 번째 앱을 띄우지 않고 현재 동작과 시작 캡처를 보여 줍니다. 시작부터 시연하려면 기존 앱을 실행한 창에서 중단한 뒤, 아래 명령으로 터미널 A에서 다시 시작합니다.

```bash
sudo -iu agent-admin
source /home/agent-admin/agent-app/agent-env.sh
whoami
env | grep -E '^(AGENT_HOME|AGENT_PORT|AGENT_UPLOAD_DIR|AGENT_KEY_PATH|AGENT_LOG_DIR)='
cd "$AGENT_HOME"
"$AGENT_HOME/agent-app-linux-x86"
```

**보여 줄 것:** agent-admin 계정, 환경 변수, Boot 5단계 `[OK]`, `Agent READY`. 앱은 실행 중 계속 로그를 출력하므로 이 터미널은 유지하고, 나머지 명령은 B에서 실행합니다.

터미널 B에서 확인합니다.

```bash
sudo ss -ltnp '( sport = :15034 )'
```

**설명:** “앱 시작 전에는 포트를 사용할 수 있는지 검사하고, 시작 후에는 실제 15034 LISTEN을 확인했습니다. 키 경로는 파일이 아니라 앱이 요구한 api_keys 디렉토리로 수정했습니다.”

**현재 증거 보완:** 기존 시작 캡처에는 5단계 OK만 보이므로, Agent READY까지 보이는 화면을 추가 캡처합니다. 아직 없는 캡처가 있다고 설명하지 않습니다.

#### 환경 변수와 실행 명령을 이해하기

| 명령 | 의미 |
|---|---|
| `sudo -iu agent-admin` | admin의 로그인 환경으로 계정 전환 |
| `source .../agent-env.sh` | 현재 셸에 환경 설정을 읽어 적용 |
| `whoami` | 지금 명령을 실행하는 계정 확인 |
| `env` | 프로그램에 전달되는 환경 변수 확인 |
| `cd "$AGENT_HOME"` | 앱 디렉토리로 이동 |
| `"$AGENT_HOME/agent-app-linux-x86"` | 앱을 절대 경로로 실행 |

환경 변수는 프로그램에 설정을 전달하는 이름과 값입니다.

| 변수 | 이 실습의 값·목적 |
|---|---|
| AGENT_HOME | `/home/agent-admin/agent-app`, 앱 위치 |
| AGENT_PORT | `15034`, 서비스 포트 |
| AGENT_UPLOAD_DIR | 앱 아래 `upload_files`, 업로드 위치 |
| AGENT_KEY_PATH | 앱 아래 `api_keys`, 키 디렉토리 |
| AGENT_LOG_DIR | `/var/log/agent-app`, 로그 위치 |

`source`가 필요한 이유는 다른 셸에서 설정한 변수가 현재 셸에 자동으로 나타나지 않기 때문입니다. 설정 파일에 쓴 값도 그 파일을 읽어야 적용됩니다. `export`는 셸 변수 값을 자식 프로그램의 환경으로 전달합니다.

#### Boot 5단계의 의미

| 단계 | 검사 내용 | 실패하면 의심할 것 |
|---|---|---|
| 1/5 User Account | 실행 계정 | skgun00이나 root로 앱을 실행했는지 |
| 2/5 Environment Variables | 필요한 환경 변수와 경로 | source 누락, 값 오타 |
| 3/5 Required Files | 필수 키 파일 등 | 파일 부재, 이름·내용·접근 권한 |
| 4/5 Port Availability | 사용할 포트가 비어 있는지 | 기존 앱이나 다른 프로그램의 점유 |
| 5/5 Log Permission | 로그 위치에 쓸 수 있는지 | 디렉토리·그룹·쓰기 권한 |

첫 키 경로 오류 때 앱은 예상값으로 `/home/agent-admin/agent-app/api_keys`를 제시했습니다. 파일 전체 경로를 넘겼던 설정을 디렉토리로 바꿔 해결했습니다. 이미 실패한 다음 단계가 “Skipped”로 표시됐다고 해서 그 단계마다 별도 원인이 있었다고 판단하지 않습니다.

#### 실행 후 로그가 계속 나오는 이유

이 앱은 실행된 상태를 유지하면서 CPU 작업과 메모리 할당에 대한 INFO 로그를 출력합니다. 명령 프롬프트가 돌아오지 않는 것은 앱이 앞에서 계속 실행 중이기 때문입니다. 다른 점검은 터미널 B에서 하고, 중단할 때는 앱이 실행 중인 A에서 Ctrl+C를 누릅니다.

**추가 질문: 왜 `./agent-app-linux-x86` 대신 절대 경로로 실행하나요?** 현재 모니터는 전체 명령행과 설정한 절대 경로의 일치를 검사합니다. 실행 방식을 맞춰야 프로세스를 정확히 찾을 수 있습니다.

**캡처 범위:** Boot 1/5부터 5/5, Agent READY까지 포함합니다. 이후 INFO 로그에 시작 화면이 밀리기 전에 캡처하거나 스크롤해 시작 부분을 보여 줍니다. 별도 터미널의 15034 LISTEN도 함께 증거로 제시합니다.

### 6. 정상 모니터 실행과 로그 확인 — 평가 1-5, 1-6, 2-1, 2-2

```bash
sudo -iu agent-admin /home/agent-admin/agent-app/bin/monitor.sh
echo "종료 코드: $?"
sudo -u agent-admin tail -n 5 /var/log/agent-app/monitor.log
```

**보여 줄 것:** 앱 PID, TCP 15034 LISTEN, UFW 상태, CPU·MEM·DISK 값, 로그 추가 메시지, 종료 코드 0. 자원 값은 실행 시점마다 달라집니다.

**구현 설명:** “pgrep으로 앱 PID를 찾고, ss로 포트 상태와 소유 PID를 확인해 서로 비교합니다. CPU는 1초 간격의 누적 시간 차이, 메모리는 MemAvailable, 디스크는 df의 `/` 사용률로 계산합니다. 앱 한 개가 아니라 리눅스 전체 자원을 측정합니다.”

**로그 설명:** “시간·PID·자원 값의 형식을 고정했고, `>>`로 이전 기록 뒤에 추가합니다. `>`를 쓰면 이전 기록이 지워집니다.”

#### 정상 출력의 각 줄 설명

```text
====== SYSTEM MONITOR RESULT ======
[HEALTH CHECK]
[OK] Process PID:4025,4026
[OK] TCP 15034 LISTEN
[OK] Firewall active (UFW)
[RESOURCES]
CPU: 0.9%
MEM: 5.5%
DISK_USED: 7%
[INFO] Log appended: /var/log/agent-app/monitor.log
종료 코드: 0
```

위 숫자는 기존 실습 결과의 예시입니다. 새 실행에서 PID와 자원 값이 달라지는 것은 정상입니다. PID가 여러 개라면 식별 조건에 맞는 프로세스가 여러 개 발견됐다는 뜻입니다. 코드에서는 발견한 PID 중 적어도 하나가 해당 포트를 소유하는지 검사합니다.

#### monitor.sh의 실행 순서

```text
환경 설정 읽기·도구 확인
→ 로그 권한과 동시 실행 잠금 확인
→ 앱 PID 확인
→ 포트 LISTEN과 소유 PID 확인
→ UFW 상태 확인
→ CPU·메모리·디스크 측정
→ 임계값 경고
→ 로그 순환 판단·새 기록 추가
```

`pgrep -f -x`는 전체 명령행이 정확히 일치하는 PID를 찾습니다. `ss -H -ltnp`는 머리글 없이 TCP LISTEN과 소유 프로세스를 보여 줍니다. 프로세스만 확인하면 앱이 초기화에 실패한 상황을 놓치고, 포트만 확인하면 다른 프로그램의 포트를 정상으로 오인할 수 있어 둘을 비교합니다.

#### CPU 계산을 숫자로 설명하기

CPU는 `/proc/stat`의 누적 카운터를 두 번 읽습니다. 첫 값 자체는 현재 사용률이 아니라 그동안 쌓인 CPU 시간입니다.

```text
1초 사이 전체 CPU 시간 증가량: 1000
같은 구간 유휴 시간 증가량: 800
일한 시간 증가량: 1000 − 800 = 200
CPU 사용률: 200 / 1000 × 100 = 20%
```

이 숫자는 계산 설명용 예시입니다. 코드는 idle과 iowait를 유휴 시간으로 취급하고, guest 시간을 중복 합산하지 않습니다. 여러 CPU 코어의 전체 카운터로 계산한 시스템 전체 사용률입니다.

#### 메모리와 디스크 계산

```text
메모리 사용률 = (MemTotal − MemAvailable) / MemTotal × 100
디스크 사용률 = df -P /의 Use% 열
```

MemAvailable은 캐시 등 재사용 가능한 메모리도 고려한 값입니다. 디스크의 `/`는 루트 파일시스템이며, Windows의 C·D 드라이브 전체를 합친 사용량이 아닙니다. 코드에서 `LC_ALL=C`를 지정해 출력 언어를 고정하고, 값이 숫자인지도 확인합니다.

#### 종료 코드와 로그 읽기

`$?`는 바로 앞 명령의 종료 코드입니다. 그래서 monitor.sh 실행 직후 `echo "종료 코드: $?"`를 해야 합니다. 그 사이 다른 명령을 넣으면 그 명령의 결과를 보게 됩니다. 정상 점검은 0, 핵심 검사 실패는 1입니다.

```text
[2026-10-08 22:33:02] PID:4185,4186 CPU:1.2% MEM:5.6% DISK_USED:7%
 └ 실행 시각              └ 앱 PID      └ 시스템 자원 값
```

**추가 질문: `>`와 `>>` 차이는?** `>`는 덮어쓰고 `>>`는 뒤에 추가합니다. 이력을 남겨 장애 전후 상태를 비교하려고 `>>`를 사용합니다. 형식도 고정해 시간·필드별 비교와 값 추출을 쉽게 했습니다.

**추가 질문: 서비스 정상까지 완전히 보장하나요?** 현재는 프로세스와 TCP 소켓 상태를 확인합니다. 앱의 실제 응답 내용까지 확인하는 검사는 별도이며, Nginx 같은 웹 대상이라면 HTTP 응답 검사로 확장할 수 있습니다.

### 7. cron 설정과 자동 로그 증가 확인 — 평가 1-7

앱을 유지한 상태에서 터미널 B로 기준값을 확인합니다.

```bash
sudo crontab -u agent-admin -l
date '+%Y-%m-%d %H:%M:%S'
sudo -u agent-admin wc -l /var/log/agent-app/monitor.log
sudo -u agent-admin tail -n 3 /var/log/agent-app/monitor.log
```

**설명:** “앞의 별 다섯 개는 매분 실행입니다. 실행 계정은 agent-admin입니다. 절대 경로를 사용하고 스크립트 내부에서 환경 설정을 읽어, 터미널 환경에 의존하지 않게 했습니다.”

모니터를 수동 실행하지 않고 다음 분이 지난 뒤 `date`, `wc`, `tail`을 다시 실행합니다. 로그 순환이 없는 상황에서 줄 수 증가와 새 시각의 기록을 보여 줍니다. 기존 증거에서는 20줄에서 21줄로 증가했습니다.

**변경 방법 설명:** “`sudo crontab -u agent-admin -e`로 기존 작업을 편집합니다. 예를 들어 `*/5 * * * *`는 매시간 0·5·10…분에 실행합니다. 과제 설정은 매분으로 유지했습니다.” 자세한 절차는 수행 내역서 **8.1절**에 있습니다.

#### crontab 한 줄을 해석하기

```cron
* * * * * /bin/bash /home/agent-admin/agent-app/bin/monitor.sh 2>&1 | /usr/bin/logger -t agent-monitor-study # agent-app-monitor-managed
```

| 부분 | 의미 |
|---|---|
| 앞의 다섯 필드 | 분·시·일·월·요일 |
| `* * * * *` | 매분 실행 |
| `/bin/bash` | Bash로 실행. 스크립트의 Bash 문법 사용 |
| 스크립트 절대 경로 | 현재 디렉토리에 관계없이 실행 파일 지정 |
| `2>&1` | 표준 오류를 표준 출력에 합침 |
| `\| /usr/bin/logger` | 출력을 시스템 로그로 전달 |
| `-t agent-monitor-study` | 시스템 로그에서 찾을 태그 지정 |
| 뒤의 `# ...` | 이 예약 작업을 식별하기 위한 셸 주석 |

cron은 자동 실행 도구이고 crontab은 그 작업 목록입니다. `sudo crontab -u agent-admin -l`의 `-u`는 대상 계정, `-l`은 목록 조회입니다. 사용자 crontab에는 시간 필드 뒤에 사용자 이름을 추가하지 않습니다.

#### 직접 등록·주기 변경하는 방법

```bash
sudo crontab -u agent-admin -l
sudo crontab -u agent-admin -e
```

기존 모니터 줄을 수정하거나, 없다면 한 줄로 추가합니다. 기존의 다른 작업은 유지하고 같은 모니터 줄을 중복 추가하지 않습니다. nano에서는 Ctrl+O → Enter → Ctrl+X로 저장하고 나옵니다. cron이 저장된 변경을 읽으므로 변경마다 서비스 재시작은 필요하지 않습니다.

| 시간 설정 | 실행 시점 |
|---|---|
| `* * * * *` | 매분 |
| `*/5 * * * *` | 매시간 0·5·10…55분 |
| `0 * * * *` | 매시간 정각 |
| `0 9 * * *` | 매일 오전 9시 |

`*/5`는 등록 순간부터 5분 뒤가 아니라 시계의 분 값에 맞춰 실행합니다. 이번 과제는 매분 설정을 유지합니다. 시간 필드와 사용자 작업 형식은 [Ubuntu 22.04 crontab 매뉴얼](https://manpages.ubuntu.com/manpages/jammy/man5/crontab.5.html)을 참고합니다.

#### 설정이 아니라 자동 실행 결과를 입증하기

`wc -l`은 파일의 줄 수, `tail -n 3`은 마지막 세 줄을 보여 줍니다. 먼저 시각·줄 수·마지막 기록을 확인하고, 앱을 유지한 채 수동 실행 없이 다음 분이 지나기를 기다립니다. 같은 명령으로 새 기록을 확인합니다.

```text
기준 확인: 22:32:13 / 20줄 / 마지막 기록 22:32:02
다음 확인: 22:33:10 / 21줄 / 마지막 기록 22:33:02
```

**발표 예시:** “등록 내용만으로 자동 실행을 판단하지 않고 다음 분의 새 기록도 확인했습니다. 이 비교 구간에는 수동 실행을 하지 않았고, 줄 수와 기록 시각이 함께 증가했습니다.”

#### 로그가 늘지 않을 때의 확인 순서

1. 앱이 실행 중이고 15034가 LISTEN인지 확인합니다.
2. cron이 active인지 확인합니다: `systemctl is-active cron`.
3. admin의 등록 내용과 스크립트 경로를 확인합니다.
4. admin으로 모니터를 직접 실행해 오류와 권한을 확인합니다.
5. cron 출력의 시스템 로그를 확인합니다.

```bash
sudo journalctl -t agent-monitor-study --since '5 minutes ago' --no-pager
```

로그 순환으로 줄 수가 줄어드는 경우도 있으므로 줄 수만 보지 않고 새 기록 시각과 백업도 확인합니다. WSL 배포판이 종료되면 cron도 계속 실행되지 않습니다. 또한 파이프 마지막의 logger 결과는 모니터의 실패 코드를 그대로 나타내지 않으므로 모니터 0/1 검사는 직접 실행으로 보여 줍니다.

<a id="step-8"></a>

### 8. 앱 중단 시 실패 처리 확인 — 평가 1-5

cron 증가 확인을 끝낸 뒤, 터미널 A에서 **Ctrl+C**로 직접 실행 중인 앱을 중단합니다. 터미널 B에서 모니터를 실행합니다.

```bash
sudo -iu agent-admin /home/agent-admin/agent-app/bin/monitor.sh
echo "종료 코드: $?"
```

**보여 줄 것:** `[ERROR] App process is not running.`과 종료 코드 1.

**설명:** “앱이 없으면 핵심 점검 실패로 판단해 1을 반환합니다. 실패 메시지는 오류 출력으로 나가며 정상 자원 로그는 추가하지 않습니다.”

시연 후에는 터미널 A에서 앞서 사용한 절대 경로로 앱을 다시 실행합니다. cron의 다음 점검이 정상 동작할 수 있도록 앱을 복구합니다.

#### 이 시험에서 검증하는 것

앱이 살아 있을 때와 없을 때의 결과 차이를 보여 주는 시험입니다. 정상 화면만 제출하면 장애 감지가 동작하는지 알 수 없으므로, 실제 중단 후 실패 코드도 확인합니다.

```text
====== SYSTEM MONITOR RESULT ======
[HEALTH CHECK]
[ERROR] App process is not running.
종료 코드: 1
```

monitor.sh의 `health_check`가 실패를 반환하면 `main`도 1로 끝납니다. 자원 수집과 정상 로그 기록은 그 뒤에 있으므로 실행되지 않습니다. 그렇다고 실패 메시지가 사라지는 것은 아니며, 직접 실행에서는 터미널에 나오고 cron 실행에서는 logger로 전달됩니다.

**추가 질문: 포트만 없어도 실패하나요?** 코드는 프로세스 부재, 지정 포트 LISTEN 부재, 앱과 포트 소유 PID 불일치 모두 실패로 처리합니다. 실습에서 실제 중단 캡처로 검증한 것은 프로세스 부재 조건이며, 세 조건을 모두 별도 실험했다고 설명하지 않습니다.

#### 중단과 복구를 끝까지 보여 주기

Ctrl+C는 앱을 실행 중인 창에서 눌러야 합니다. 점검용 터미널 B에서 Ctrl+C를 눌렀다고 A의 앱이 종료되는 것은 아닙니다. 중단 뒤에도 프로세스나 포트가 남아 있으면 다른 실행 인스턴스가 있는지 확인합니다.

```bash
sudo ss -ltnp '( sport = :15034 )'
pgrep -f -x -- /home/agent-admin/agent-app/agent-app-linux-x86
```

시험 후 A에서 앱을 다시 실행하고 B에서 모니터와 종료 코드 0을 확인합니다. 장애를 만들었다는 것에서 끝내지 않고, 다시 정상으로 돌아왔다는 결과까지 보여 줍니다.

<a id="step-9"></a>

### 9. 경고 처리와 최소 권한 설명 — 평가 2-3, 3-3

```bash
sudo -l -U agent-admin
```

**보여 줄 것:** 비밀번호 없이 허용된 관리자 명령은 `/usr/sbin/ufw status`뿐입니다. 모든 관리자 명령을 허용한 것이 아닙니다.

경고 테스트는 수행 내역서 **6절**의 명령과 결과를 보여 줍니다. CPU 21%, MEM 11%, DISK 81%의 가상 입력과 inactive 응답으로 경고를 확인했으며, 실제 방화벽을 끄지는 않았습니다.

**설명:** “프로세스·포트 부재는 실패로 종료하고, 자원 초과나 방화벽 비활성은 경고 후 계속 점검합니다. 경고 하나로 중단하면 다른 상태와 로그를 놓칠 수 있기 때문입니다.”

#### 최소 권한을 실제로 확인하기

```text
(root) NOPASSWD: /usr/sbin/ufw status
```

`NOPASSWD`는 여기에 지정된 명령을 실행할 때 비밀번호를 요구하지 않는다는 뜻입니다. admin에게 모든 sudo 권한을 줬다는 뜻이 아닙니다. 코드에서는 `sudo -n /usr/sbin/ufw status`를 사용합니다. `-n`은 비밀번호를 물으며 기다리지 않고, 인증이 필요하면 실패하도록 하는 옵션입니다.

현재 admin 권한으로 조회 가능한지는 다음처럼 확인할 수 있습니다.

```bash
sudo -u agent-admin sudo -n /usr/sbin/ufw status
```

#### 임계값과 경고 의미

| 항목 | 경고 조건 | 경계값과의 관계 |
|---|---|---|
| CPU | 20% 초과 | 20%는 경고하지 않고 21%는 경고 |
| MEM | 10% 초과 | 10%는 경고하지 않고 11%는 경고 |
| DISK_USED | 80% 초과 | 80%는 경고하지 않고 81%는 경고 |
| UFW | 비활성 또는 조회 실패 | 메시지를 출력하고 계속 점검 |

경고는 운영자가 확인할 이상 징후입니다. 경고 후 계속 실행하는 것은 그 상태를 안전하다고 판단한다는 뜻이 아니라, 남은 상태 수집과 기록도 수행한다는 뜻입니다. 메모리 10% 등은 이 과제의 설정이며 모든 서버에 공통으로 적절한 운영 기준이라고 주장하지 않습니다.

#### 경고 시험을 직접 재현하는 명령

```bash
sudo -iu agent-admin /bin/bash <<'BASH'
set -e
source /home/agent-admin/agent-app/bin/monitor.sh

warn_if_over CPU 21.0 20
warn_if_over MEM 11.0 10
warn_if_over DISK_USED 81 80

ufw_status() { printf 'Status: inactive\n'; }
check_firewall
echo '[TEST] 경고 후에도 계속 실행됨'
BASH
echo "테스트 종료 코드: $?"
```

소스로 읽을 때는 함수만 정의하고 main을 실행하지 않도록 스크립트 끝에 조건이 있습니다. 위 명령은 그 함수에 가상 값을 전달하고, 이 테스트 셸 안에서만 UFW 조회 응답을 바꿉니다. 실제 방화벽 설정, 자원 사용률, 운영 로그에 가상 값을 쓰지는 않습니다.

**보여 줄 것:** 경고 네 개, 마지막 TEST 문장, 종료 코드 0. 이 시험은 경고 함수와 계속 실행 정책을 검증하며 실제 자원을 임계값 이상 사용한 시험과 구분합니다.

<a id="step-10"></a>

### 10. 로그 순환 설명 — 평가 1-8, 2-4

수행 내역서 **9절**의 테스트 명령과 결과를 보여 줍니다. 실제 운영 로그를 크게 늘리지 않고 임시 디렉토리에서 검증했습니다.

**설명:** “새 줄을 더했을 때 10MiB를 초과하면 기존 로그를 순환합니다. 가장 오래된 `.9`를 지우고, 큰 번호부터 이동한 뒤 현재 로그를 `.1`로 바꿉니다. 새 현재 로그와 백업 9개, 총 10개를 유지합니다. flock으로 동시 실행의 기록·순환 충돌도 막았습니다.”

**보여 줄 것:** 백업 `.1`의 10,485,760바이트, 새 로그의 `rotation-test`, 총 파일 수 10개, 테스트 종료 코드 0. 이 용량 관리는 필수이며, 기간별 압축·삭제 보너스는 구현하지 않았습니다.

#### 10MB와 10개를 구체적으로 설명하기

코드의 기준은 `10 * 1024 * 1024`바이트인 10MiB입니다. 일반 십진수 10MB인 10,000,000바이트와 구분해서 설명합니다. 순환 조건은 `현재 크기 + 새 줄 크기 + 줄바꿈 > 기준`이므로, 쓰고 난 뒤 확인하는 것이 아니라 먼저 판단합니다.

```text
회전 전: monitor.log / .1 / .2 / … / .9
1. 기존 .9 삭제
2. .8 → .9, .7 → .8, …, .1 → .2
3. monitor.log → .1
4. 새 monitor.log에 다음 기록 작성
회전 후: 현재 파일 1개 + 백업 9개 = 최대 10개
```

큰 번호부터 이동해야 옮길 목적지에 남아 있는 파일을 먼저 정리할 수 있습니다. `.1`이 최신 백업이고 `.9`가 가장 오래된 백업입니다. “백업 10개와 현재 1개”가 아니라 현재 포함 10개입니다.

#### 임시 디렉토리에서 순환 검증하기

다음은 기존 실습과 같은 방식의 시험입니다. 운영 로그 경로를 변경하지 않고 테스트 셸의 LOG_FILE만 임시 경로로 지정합니다.

```bash
sudo -iu agent-admin /bin/bash <<'BASH'
set -e
source /home/agent-admin/agent-app/bin/monitor.sh
rotation_dir=$(mktemp -d /tmp/agent-rotation-test.XXXXXX)
LOG_FILE="$rotation_dir/monitor.log"

for n in {1..9}; do
    printf 'backup-%s\n' "$n" > "$LOG_FILE.$n"
done
truncate -s $((10*1024*1024)) "$LOG_FILE"
write_log 'rotation-test'

stat -c '%n : %s bytes' "$LOG_FILE" "$LOG_FILE".[1-9]
file_count=$(find "$rotation_dir" -type f -name 'monitor.log*' | wc -l)
echo "로그 파일 수: $file_count"
test "$file_count" -eq 10
test "$(cat "$LOG_FILE.9")" = 'backup-8'
cat "$LOG_FILE"
echo '[PASS] 용량 기준 순환과 최대 10개 유지 확인'
BASH
echo "테스트 종료 코드: $?"
```

`mktemp -d`는 겹치지 않는 임시 디렉토리를 만들고, `truncate`는 시험용 파일의 크기를 지정합니다. `stat -c %s`는 바이트 크기를 출력합니다. 새 현재 로그는 14바이트이고 `.1`은 10,485,760바이트입니다. 기존 backup-8이 `.9`로 이동했는지도 확인해 단순히 파일 수만 맞는 경우를 구분했습니다. 끝의 PASS와 종료 코드 0이 시험 성공 증거입니다.

#### 동시 실행과 정책 범위

수동 점검과 cron이 겹칠 수 있습니다. `flock -n`으로 로그 디렉토리의 잠금을 얻은 실행만 점검·기록하고, 이미 실행 중이면 중복 실행을 건너뜁니다. 이 기능은 중복 실행 충돌을 예방하려는 구현이며, 별도 동시 실행 시험 결과가 있다고 주장하지 않습니다.

정상 운용에서 최대 크기와 개수로 monitor.log 계열의 용량을 제한합니다. 다른 앱 로그와 시스템 로그는 이 정책의 대상이 아닙니다. 기간별 압축·삭제나 통계 보고서는 보너스이므로 구현하지 않았습니다.

<a id="step-11"></a>

### 11. 상황 변경·장애 대응 질문 답변 — 평가 항목 4

수행 내역서 **10.4절**을 바탕으로 말합니다.

- **Nginx로 바뀐다면:** 프로세스 구조·식별 조건, 서비스 포트, 로그 경로·권한, 임계값을 수정합니다. 웹 응답까지 검사하려면 HTTP 점검을 추가할 수 있습니다.
- **프로세스는 있는데 포트가 없다면:** 실행 명령 → ss의 LISTEN·소유 PID → 앱 로그 → 설정·포트 충돌·권한 순서로 확인합니다. 로컬 LISTEN이 정상인데 외부 연결만 실패할 때 방화벽과 WSL 네트워크를 확인합니다.
- **로그로 디스크가 찰 위험이 있다면:** 큰 파일과 발생 원인을 찾고 필요한 증거를 보존한 뒤 정리·출력 축소를 합니다. 이후 모든 로그의 순환 정책과 디스크 감시를 점검합니다. 현재 정책은 monitor.log에만 적용됩니다.

#### 질문 A: Nginx로 바뀌면 파일명만 고치면 되나요?

“프로세스의 실제 실행 명령과 master·worker 관계를 먼저 확인하겠습니다. 현재의 전체 명령행 일치 조건을 그대로 쓰면 프로세스를 놓칠 수 있습니다. 서비스 포트와 포트 소유 관계, 로그 경로·권한, 임계값을 맞추겠습니다. HTTP 응답까지 보려면 TCP 소켓 점검 뒤에 응답 코드나 필요한 내용을 확인하는 검사를 추가하겠습니다.”

**이해 포인트:** 프로그램마다 정상 상태의 조건이 다릅니다. 현재 시스템 자원 측정 함수는 재사용할 수 있지만, 앱 자체의 CPU·메모리 사용량을 원한다면 측정 방식도 별도로 바꿔야 합니다. 이번 제출에서 Nginx 전환을 구현한 것은 아닙니다.

#### 질문 B: 프로세스가 있는데 포트가 없으면 방화벽부터 열면 되나요?

“먼저 앱이 실제로 LISTEN 소켓을 만들었는지 확인하겠습니다. 앱이 초기화 중이거나 설정 오류, 포트 충돌, 권한 문제로 소켓을 만들지 못했다면 방화벽 허용으로 해결되지 않습니다. 로컬 LISTEN은 정상인데 외부 접속만 실패할 때 방화벽과 WSL 경로를 조사하겠습니다.”

| 확인 단계 | 명령·자료 | 판단 목적 |
|---|---|---|
| 실행 프로세스 | `ps`·`pgrep` | 기대한 앱과 실행 명령인지 |
| 실제 소켓 | `ss -ltnp` | 주소·포트·소유 PID가 맞는지 |
| 앱 로그 | 시작·오류 출력 | 초기화 지연, bind 실패, 설정 오류 |
| 설정·권한 | 환경 변수·경로·포트 점유 | 잘못된 값과 접근 제한 |
| 외부 연결 경로 | UFW·WSL 네트워크 | 로컬 정상 이후 외부 실패 원인 |

#### 질문 C: 디스크가 곧 가득 차면 로그를 전부 지우면 되나요?

“먼저 어떤 파일시스템과 로그가 커졌는지 찾고, 필요한 장애 증거를 보존하겠습니다. 단기적으로 오래된 기록을 정책에 따라 정리하거나 출력 수준을 줄입니다. 중기적으로 순환 정책과 모든 로그 발생 경로, 디스크 경고를 점검하겠습니다. monitor.log만 제한한다고 전체 디스크 증가가 멈추는 것은 아닙니다.”

**이해 포인트:** 용량 확보와 원인 분석에 필요한 증거 보존을 함께 고려합니다. 같은 이름의 다른 디렉토리나 다른 앱 로그를 무조건 지우지 않고 대상과 원인을 확인합니다. 이 설명은 운영 대응 질문에 대한 답변이며 보너스 자동 삭제 기능을 추가한 것은 아닙니다.
