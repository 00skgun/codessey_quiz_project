## 2. 기본 보안 및 네트워크

`openssh-server`와 `acl` 등 필요한 도구를 설치했습니다. `/etc/ssh/sshd_config.d/00-agent-mission.conf`는 다음과 같습니다.

```text
Port 20022
PermitRootLogin no
```

`sshd -t`로 문법을, `sshd -T`로 Include가 적용된 유효 설정을 확인했습니다. 단순히 파일에 문자열이 있는지만 검사하지 않았습니다. `ss`에서 실제 SSH 리스너도 확인했습니다.

```text
port 20022
permitrootlogin no
0.0.0.0:20022 LISTEN (sshd)
[::]:20022 LISTEN (sshd)
```

UFW는 다음 순서로 설정했습니다. 기존의 다른 사용자 규칙이 있으면 스크립트가 중단하도록 하여 기존 규칙을 일괄 초기화하지 않았습니다.

```bash
ufw allow 20022/tcp
ufw allow 15034/tcp
ufw default deny incoming
ufw default allow outgoing
ufw --force enable
systemctl enable ssh
systemctl restart ssh
```

실제 `ufw status verbose`의 주요 내용:

```text
Status: active
Default: deny (incoming), allow (outgoing), deny (routed)
20022/tcp       ALLOW IN    Anywhere
15034/tcp       ALLOW IN    Anywhere
20022/tcp (v6)  ALLOW IN    Anywhere (v6)
15034/tcp (v6)  ALLOW IN    Anywhere (v6)
```

IPv4와 IPv6에 각각 같은 두 포트만 사용자 허용 규칙으로 등록했습니다. UFW 기본 루프백/연결 추적 동작은 유지했습니다. Windows 방화벽이나 외부 공유기 포트 포워딩은 변경하지 않았으며, 외부 PC의 SSH 인증 접속은 검증 범위에 포함하지 않았습니다.

## 3. 계정, 그룹, 디렉터리와 권한

| 계정 | 역할 | 공통 그룹 | 핵심 그룹 |
| --- | --- | --- | --- |
| agent-admin | 앱 운영, cron 실행 | agent-common | agent-core |
| agent-dev | monitor.sh 소유자 | agent-common | agent-core |
| agent-test | QA, 업로드 공유 | agent-common | 가입하지 않음 |

계정은 `useradd -m -s /bin/bash`, 그룹은 `groupadd`, 보조 그룹은 `usermod -aG`로 설정했습니다. 세 계정에 포괄적인 sudo 권한을 부여하지 않았습니다.

| 경로 | 소유자:그룹 | 모드/정책 |
| --- | --- | --- |
| `/home/agent-admin/agent-app` | agent-admin:agent-common | 2750 |
| `.../upload_files` | agent-admin:agent-common | 2770 + default ACL |
| `.../api_keys` | agent-admin:agent-core | 2770 + default ACL |
| `/var/log/agent-app` | agent-admin:agent-core | 2770 + default ACL |
| `.../bin/monitor.sh` | agent-dev:agent-core | **750** |
| `.../api_keys/t_secret.key` | agent-admin:agent-core | 660 |

공유 디렉터리에 setgid를 설정하여 새 항목의 그룹이 유지되게 했습니다. default ACL은 `user::rwx, group::rwx, mask::rwx, other::---`입니다. 또한 `/home/agent-admin`에 `group:agent-common:--x` ACL을 부여해 상위 디렉터리를 통과할 수 있게 했습니다.

실제 시험에서는 임시 파일을 생성하여 다음을 확인하고 그 시험 파일을 정리했습니다.

- admin이 `umask 077`로 만든 파일을 dev가 읽고 덧쓸 수 있음: 세 디렉터리 모두 통과.
- test가 `upload_files` 파일을 읽고 덧쓸 수 있음: 통과.
- test가 `api_keys`와 로그 디렉터리의 파일을 읽거나 쓰려고 하면 거부됨: 통과.
- `stat` 결과: `agent-dev agent-core 750 /home/agent-admin/agent-app/bin/monitor.sh`.

파일을 생성할 때의 권한을 default ACL로 제어하며, 프로그램이 이후 명시적으로 `chmod`하면 유효 접근 권한이 달라질 수 있으므로 실제 접근 시험도 함께 수행했습니다.

## 5. monitor.sh 구현 및 실제 실행

`monitor.sh`는 Bash로 작성했습니다. Python은 관제 자동화를 대신하는 데 사용하지 않았습니다. 실행 대상 바이너리의 프로세스 경로를 `/proc`에서 확인하고, TCP 15034 리스너의 소유 PID가 앱 PID 중 하나인지 확인합니다. 두 조건 중 하나라도 실패하면 종료 코드 1입니다.

방화벽이 비활성화되거나 상태를 읽을 수 없으면 경고를 출력하고 측정과 로그 기록을 계속합니다. cron은 `sudo -n /usr/sbin/ufw status`만 비밀번호 없이 실행할 수 있습니다. sudoers 설정은 `visudo -cf`로 검증했습니다.

| 측정 | 계산/출처 | 경고 조건 |
| --- | --- | --- |
| CPU | `/proc/stat`을 1초 간격으로 읽어 전체/유휴 카운터 변화량 계산 | > 20% |
| MEM | `(MemTotal - MemAvailable) / MemTotal × 100` | > 10% |
| DISK_USED | `df -P /`의 Used% | > 80% |

세 값은 앱 단독 사용량이 아닌 시스템 사용량입니다. CPU의 guest 카운터를 중복 합산하지 않습니다. 임계값과 같은 경우에는 경고하지 않습니다.

실제 수동 실행 결과:

```text
Process agent-app-linux-x86... [OK] (PID: 2113,2120)
TCP 15034 LISTEN... [OK]
Firewall... [OK] active (ufw)
CPU Usage : 1.1%
MEM Usage : 4.8%
DISK Used : 6%
[INFO] Log appended: /var/log/agent-app/monitor.log
```

PID가 두 개인 것은 제공 단일 파일 실행 프로그램의 부모 프로세스와 실제 작업 프로세스를 함께 식별했기 때문입니다. 당시 실제 자원 수치는 임계값보다 작아 경고가 없었습니다. 초과 경고의 동작은 합성 입력 테스트에서 별도로 검증했습니다.

로그 형식과 첫 실제 기록:

```text
[2026-09-05 21:41:01] PID:2113,2120 CPU:1.1% MEM:4.8% DISK_USED:6%
```

매번 기록 전에 예상 파일 크기를 검사합니다. 10 MiB를 넘게 되면 파일을 회전하고 `monitor.log`와 `.1`~`.9`, **현재 파일을 포함한 총 10개**를 유지합니다. 가장 오래된 `.9`를 제거한 뒤 기존 파일의 순서를 이동합니다. `flock`으로 동시에 실행된 모니터가 같은 로그를 기록하거나 회전하지 못하도록 했습니다.

## 6. cron과 자동 로그 누적

`cron.service`를 활성화하고 **agent-admin의 crontab**에 다음 한 줄을 등록했습니다. 기존의 다른 cron 작업은 유지합니다.

```cron
* * * * * /bin/bash /home/agent-admin/agent-app/bin/monitor.sh 2>&1 | /usr/bin/logger -t agent-monitor # agent-app-monitor-managed
```

모니터 자체가 환경 파일을 읽으므로 로그인 셸의 `.bashrc`에 의존하지 않습니다. 콘솔 출력과 오류는 시스템 저널의 `agent-monitor` 태그에 남깁니다.

자동 실행 검증은 수동 실행 직후의 `monitor.log` 줄 수와 마지막 시각을 기록하고, **수동 모니터 실행 없이 70초를 기다린 뒤** 비교했습니다. 전후 기록과 cron의 시스템 저널은 [cron-auto.txt](evidence/cron-auto.txt)에 저장했습니다.

| 확인 | 시각 | 줄 수 | 마지막 로그 시각 |
| --- | --- | --- | --- |
| 대기 전 | 2026-09-05 21:41:01 | 1 | 21:41:01 |
| 70초 대기 후 | 2026-09-05 21:42:11 | 2 | 21:42:02 |

```text
[2026-09-05 21:41:01] PID:2113,2120 CPU:1.1% MEM:4.8% DISK_USED:6%
[2026-09-05 21:42:02] PID:2113,2120 CPU:1.1% MEM:6.0% DISK_USED:6%
```

시스템 저널에도 21:42:01의 cron 시작과 21:42:02의 로그 기록이 남았습니다. 그 뒤 21:42:13에 증거 수집 도구가 수동 모니터를 한 번 더 실행하여 최종 사본은 3줄입니다. **세 줄 전체가 cron으로 생성된 것은 아니며, 21:42:02의 추가 기록이 이 시험의 자동 실행 증거**입니다.

## 7. 검증과 선택 보너스

Ubuntu의 Bash로 모든 `.sh` 파일의 문법을 검사했습니다. 21:48:16 최종 검증에서 설치된 스크립트와 제출 소스의 일치, 원본 앱 해시, 키 링크, app/cron/ssh 서비스 활성 상태도 확인했습니다. [final-check.txt](evidence/final-check.txt)

`tests/run-tests.sh`의 14개 시험은 다음 범위를 검증합니다.

- 정상 로그 형식과 경고 임계값 경계.
- 프로세스 없음, 포트 없음, 다른 프로세스의 포트.
- 방화벽 비활성 및 상태 조회 실패 시 경고 후 계속 실행.
- CPU/MEM/DISK 초과 경고와 CPU 카운터 오류, 메모리 조회 오류.
- 12회 회전 후 현재+백업 10개, 각 파일 10 MiB 이하.
- 중복 실행 잠금.
- 통계 평균 및 잘못된 행 제외, 시작/종료 시각 포함, 빈 입력과 잘못된 날짜 처리.

선택 보너스 1인 `report.sh`는 CPU/MEM/DISK의 평균·최대·최소, 극값 발생 시각과 샘플 수를 출력합니다. 시작/종료 시각을 지정할 수 있습니다. 실제 로그 3개를 분석한 결과는 [report.txt](evidence/report.txt)에 저장했습니다.

| 자원 | 평균 | 최대 | 최소 |
| --- | --- | --- | --- |
| CPU | 1.2% | 1.5% | 1.1% |
| MEM | 5.5% | 6.0% | 4.8% |
| DISK_USED | 6.0% | 6.0% | 6.0% |

Ubuntu 기본 awk에서 문자열 정리 후 명시적인 숫자 변환을 적용하고, 구간 반복 정규식에 의존하지 않도록 수정했습니다. 합성 테스트를 실제 자원 측정이나 서버 설정 증거로 대신 사용하지 않았습니다.

WSL에서 systemd 서비스만 실행 중인 상태가 인스턴스의 지속 실행을 보장하지는 않습니다. 시연과 cron 확인 중에는 Ubuntu 터미널을 열어 둡니다. [Microsoft WSL 설명](https://learn.microsoft.com/en-us/windows/wsl/systemd)
