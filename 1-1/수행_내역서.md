# 리눅스 서버 상태 점검 자동화 수행 내역서

- 미션: 컴퓨터가 알아서 자기 상태를 점검하게 만들기
- 수행일: 2026-10-08 (대한민국 시간)
- 실습 환경: WSL2 / Ubuntu 22.04.5 LTS / x86-64 / systemd
- 제출물: 이 수행 내역서와 별도 파일 `monitor.sh`
- 범위: 필수 과제. 보너스 통계 리포트 및 7일 압축·30일 삭제 정책은 제외한다.

> 이 문서는 대화에서 사용자가 실행하고 결과를 공유한 내용과 제공한 기존 소스코드를 바탕으로 작성했다. 기존 환경에 이미 존재하던 계정·그룹·보안 설정·스크립트를 점검하고, 실행 환경의 불일치를 수정한 뒤 기능을 검증했다. 계정 생성이나 스크립트 최초 작성을 이번 실습에서 새로 수행했다고 기록하지 않는다.
>
> 사용자가 이 대화에 보내 준 캡처를 내용 변경 없이 captures 폴더에 저장하고, 해당 항목에 상대 경로로 연결했다. 교체 요청이 있었던 ACL 사진은 최신 사진을 사용했다. 문서를 옮길 때는 captures 폴더도 함께 옮긴다.
>
> 최종 보완 항목: 최신 앱 시작 사진에서 Boot 5단계의 `[OK]`는 확인했으나, 사진 하단에 `Agent READY`가 보이지 않는다. 해당 문구가 보이는 캡처를 추가한 뒤 제출한다.

## 1. 과제 목적과 전체 흐름

리눅스 서버에 필요한 접속 보안과 역할별 접근 권한을 구성하고, 제공 앱의 상태와 시스템 자원 사용량을 Bash 스크립트로 점검·기록한다. cron으로 점검을 매분 실행하고, 로그의 용량과 보관 개수를 제한해 지속적으로 운영할 수 있게 한다.

```text
접속 보안 확인 → 계정·디렉토리 권한 확인 → 앱 실행 환경 구성
→ 앱 시작·포트 확인 → 상태 점검·로그 기록 → cron 자동 실행 → 로그 용량 관리
```

서비스가 동작하는지뿐 아니라, 명령을 선택한 이유와 권한 정책, 장애 상황의 확인 순서까지 설명하는 것을 목표로 한다.

### 3.3 SSH 포트·Root 접속 설정을 변경하는 방법

아래는 이 실습의 Ubuntu 22.04/systemd 환경에서 설정을 변경하는 절차다. 이미 확인한 결과와 구분한 재현 안내이며, 문서 작성 중 서버 설정을 다시 변경하지는 않았다. 명령은 관리자 권한을 사용할 수 있는 skgun00의 Ubuntu 터미널에서 실행한다.

#### 단계 1: 현재 설정 위치 확인과 백업

```bash
sudo grep -RnsE '^[[:space:]]*(Include|Port|PermitRootLogin|Match)[[:space:]]' \
  /etc/ssh/sshd_config /etc/ssh/sshd_config.d

ssh_backup_stamp=$(date +%Y%m%d-%H%M%S)
sudo cp -a /etc/ssh/sshd_config "/etc/ssh/sshd_config.backup-$ssh_backup_stamp"
sudo cp -a /etc/ssh/sshd_config.d "/etc/ssh/sshd_config.d.backup-$ssh_backup_stamp"
```

설정은 `/etc/ssh/sshd_config`와 여기서 포함하는 `/etc/ssh/sshd_config.d/*.conf`에 있을 수 있다. Ubuntu의 기본 Include 위치 때문에 추가 설정 파일의 값이 본문보다 먼저 적용될 수 있다. `PermitRootLogin`은 먼저 읽힌 값을 확인해야 하고, `Port`는 여러 값을 지정할 수 있으므로 중복 포트 설정도 살펴본다. [Ubuntu 22.04 OpenSSH 설정 매뉴얼](https://manpages.ubuntu.com/manpages/jammy/man5/sshd_config.5.html).

#### 단계 2: 설정 파일 편집

```bash
sudo nano /etc/ssh/sshd_config
```

전역 설정 영역에서 다음 두 설정을 사용한다. 줄 앞의 `#`는 주석이므로 실제 적용할 줄에는 붙이지 않는다. 기존의 활성화된 `Port`나 `PermitRootLogin` 줄은 목적에 맞게 수정하고, 같은 설정을 계속 덧붙이지 않는다. `Match` 아래는 특정 연결에만 적용되는 영역이므로, 아래 두 줄은 첫 `Match` 앞의 전역 영역에 둔다.

```text
Port 20022
PermitRootLogin no
```

단계 1에서 `.conf` 파일에 같은 설정이 발견됐다면 그 파일도 `sudo nano 실제파일경로`로 확인·수정한다. 예를 들어 다른 활성 `Port 22`가 있으면 20022만 사용하도록 정리한다. `PermitRootLogin yes`가 먼저 적용되고 있으면 해당 값을 `no`로 수정한다. 마지막에는 다음 단계의 `sshd -T` 결과를 기준으로 판단한다.

nano에서 `Ctrl+O` → Enter로 저장하고, `Ctrl+X`로 나온다.

#### 단계 3: 새 포트 허용과 문법·적용 예정 값 검사

```bash
sudo ufw allow 20022/tcp
sudo /usr/sbin/sshd -t
sudo /usr/sbin/sshd -T | grep -E '^(port|permitrootlogin) '
```

`sshd -t`는 정상일 때 보통 출력이 없다. 오류가 있으면 표시된 파일과 줄을 수정한 뒤 다시 검사한다. `sshd -T`의 목표 결과는 `port 20022` 하나와 `permitrootlogin no`다. 다른 포트가 추가로 나오거나 Root 설정이 다르면 앞서 확인한 설정 파일의 중복·우선순위를 다시 확인한다.

#### 단계 4: 서비스에 반영하고 실행 상태 확인

```bash
sudo /usr/sbin/sshd -t && sudo systemctl restart ssh
systemctl is-active ssh
sudo ss -ltnp | grep sshd
```

`&&`는 왼쪽 문법 검사가 성공한 경우에만 오른쪽 재시작을 실행한다. `active`와 20022 LISTEN이 보이는지 확인한다. 설정 파일 수정만으로 실행 중인 서버의 접속 포트가 자동 변경되는 것은 아니다.

SSH로 원격 작업 중이라면 기존 접속 창을 유지하고, 새 터미널에서 변경된 포트 접속을 확인한다. 이 실습의 Ubuntu 내부에서 로컬 SSH를 시험하는 명령은 다음과 같다.

```bash
ssh -p 20022 skgun00@127.0.0.1
```

접속에는 해당 계정에 설정된 비밀번호나 허용된 SSH 키가 필요하다. 다른 컴퓨터에서는 `127.0.0.1`을 서버 주소로 바꾸고, WSL까지의 네트워크 경로도 별도로 구성·확인해야 한다.

#### 단계 5: 이전 방화벽 허용 규칙 정리

```bash
sudo ufw status numbered
```

새 포트 접속을 확인한 뒤 이전 22번 허용 규칙이 실제로 남아 있다면 그 규칙만 제거한다. 이 실습에서 확인한 최종 상태에는 이미 20022와 15034만 있으므로 삭제 작업은 필요 없다.

예를 들어 목록에 `22/tcp ALLOW` 규칙이 있을 때만 다음 명령을 사용한다.

```bash
sudo ufw delete allow 22/tcp
sudo ufw status verbose
```

규칙이 `OpenSSH` 프로필로 등록돼 있다면 그 프로필을 기준으로 삭제한다. SSH 포트 변경은 접속을 받는 번호의 변경이고, UFW 변경은 그 번호로 들어오는 연결의 허용 여부 변경이다. 둘을 함께 확인해야 한다.

### 4.2 디렉토리와 ACL

```bash
sudo ls -ld \
  /home/agent-admin \
  /home/agent-admin/agent-app \
  /home/agent-admin/agent-app/upload_files \
  /home/agent-admin/agent-app/api_keys \
  /var/log/agent-app

sudo getfacl -p \
  /home/agent-admin \
  /home/agent-admin/agent-app \
  /home/agent-admin/agent-app/upload_files \
  /home/agent-admin/agent-app/api_keys \
  /var/log/agent-app
```

| 경로 | 소유 그룹 | 주요 정책 |
| --- | --- | --- |
| /home/agent-admin | agent-admin | ACL로 agent-common에 경로 통과 권한 부여 |
| /home/agent-admin/agent-app | agent-common | 그룹 읽기·경로 통과 허용 |
| upload_files | agent-common | 세 계정에 읽기·쓰기·경로 통과 허용 |
| api_keys | agent-core | 운영자·개발자에 읽기·쓰기·경로 통과 허용 |
| /var/log/agent-app | agent-core | 운영자·개발자에 읽기·쓰기·경로 통과 허용 |

상위 홈 디렉토리에는 `group:agent-common:--x` ACL이 있었다. 공용 그룹에 홈 폴더 목록 조회 권한을 주지 않고, 알고 있는 하위 경로로 통과할 수 있도록 한 구성이다.

디렉토리의 `r`은 목록 조회, `w`는 항목 생성·삭제, `x`는 경로 통과 권한이다. 그룹 권한에 있는 setgid(`s`)는 새 항목의 그룹 상속에 사용된다. 기본 ACL(`default:`)은 새 항목의 접근 권한 규칙을 물려주는 데 사용된다. 파일 생성 시 요청한 모드나 이후 chmod에 따라 최종 권한이 제한될 수 있으므로, 그룹 상속과 권한 상속은 구분해야 한다.

## 5. 앱 실행 환경과 오류 해결

### 5.1 환경 변수와 실행 계정

![초기 환경 확인 — agent-admin 로그인 환경에서 AGENT 변수가 출력되지 않은 상태](captures/05-env-initial.png)

*초기 환경 확인 — agent-admin 로그인 환경에서 AGENT 변수가 출력되지 않은 상태*

```bash
sudo -iu agent-admin
```

앱은 일반 계정 `agent-admin`으로 실행했다. 최종 공용 환경 설정 파일 `/home/agent-admin/agent-app/agent-env.sh`의 값은 다음과 같다.

```bash
export AGENT_HOME=/home/agent-admin/agent-app
export AGENT_PORT=15034
export AGENT_UPLOAD_DIR=/home/agent-admin/agent-app/upload_files
export AGENT_KEY_PATH=/home/agent-admin/agent-app/api_keys
export AGENT_LOG_DIR=/var/log/agent-app
```

### 6.2 기능별 구현과 선택 이유

| 기능 | 구현 | 선택 이유 |
| --- | --- | --- |
| 프로세스 식별 | pgrep -f -x | 명령행 전체를 절대 경로와 일치시키고 단순 부분 문자열 오인을 줄임 |
| 포트 확인 | ss -H -ltnp, 지정 포트 필터 | TCP LISTEN 상태와 소유 PID를 함께 확인 |
| 프로세스·포트 관계 | 앱 PID와 ss의 PID 비교 | 다른 프로그램이 포트를 차지한 경우를 구분 |
| 방화벽 상태 | sudo -n /usr/sbin/ufw status | 비대화형 cron에서 허용된 조회 명령만 실행 |
| CPU | /proc/stat, awk, 1초 샘플링 | 누적 CPU 시간의 변화량으로 사용률 계산 |
| 메모리 | /proc/meminfo의 MemTotal·MemAvailable | 사용 가능 메모리를 기준으로 시스템 사용률 계산 |
| 루트 디스크 | df -P /, awk | 일정한 출력 형식에서 루트 파일시스템 사용률 추출 |
| 경고 비교 | awk의 소수 비교 | 소수점 사용률을 임계값과 비교 |
| 로그 추가 | printf와 >> | 기존 기록 유지 |
| 로그 순환 | stat, mv, rm | 다음 기록을 추가하기 전에 크기와 파일 개수 관리 |
| 중복 실행 방지 | flock | 수동 실행과 cron이 겹칠 때 로그 쓰기·순환 충돌 방지 |

CPU는 전체 누적 시간에서 idle+iowait를 유휴 시간으로 취급해 두 시점의 변화량으로 계산한다. guest 항목은 중복 합산하지 않는다.

```text
CPU(%) = (전체 시간 변화량 - 유휴 시간 변화량) / 전체 시간 변화량 × 100
MEM(%) = (MemTotal - MemAvailable) / MemTotal × 100
DISK_USED(%) = df -P /에서 추출한 Used %
```

수집 값은 앱 단독 사용률이 아니라 WSL 리눅스 환경 전체의 사용률이다. `LC_ALL=C`로 숫자와 명령 출력의 언어를 일정하게 하고, 필요한 PATH를 지정해 cron 실행 환경에서도 동작하도록 구성했다.

### 6.3 실패와 경고의 구분

| 조건 | 처리 |
| --- | --- |
| 앱 프로세스 없음 | 오류 출력, 종료 코드 1 |
| TCP 15034 LISTEN 없음 | 오류 출력, 종료 코드 1 |
| 포트가 앱 소유가 아님 또는 PID를 읽을 수 없음 | 오류 출력, 종료 코드 1 |
| 방화벽 비활성·조회 실패 | WARNING, 계속 진행 |
| CPU > 20% | WARNING, 계속 진행 |
| MEM > 10% | WARNING, 계속 진행 |
| DISK_USED > 80% | WARNING, 계속 진행 |

임계값과 같은 값은 초과가 아니므로 경고 대상이 아니다. 자원 수집·로그 쓰기 자체의 오류는 성공으로 처리하지 않는다.

로그 형식:

```text
[YYYY-MM-DD HH:MM:SS] PID:... CPU:..% MEM:..% DISK_USED:..%
```

시간과 필드 이름을 고정해 비교·파싱하기 쉽게 했다. `>`는 기존 파일 내용을 덮어쓰고, `>>`는 뒤에 추가하므로 누적 로그에는 `>>`를 사용했다.

## 8. cron 매분 자동 실행

```bash
sudo crontab -u agent-admin -l
```

확인된 등록 내용:

```cron
* * * * * /bin/bash /home/agent-admin/agent-app/bin/monitor.sh 2>&1 | /usr/bin/logger -t agent-monitor-study # agent-app-monitor-managed
```

다섯 필드는 분·시·일·월·요일이며, 모두 `*`이면 매분 실행한다. `2>&1`은 오류 출력을 일반 출력과 합치고, logger는 콘솔 출력을 시스템 로그로 전달한다. 지정된 monitor.log는 스크립트 내부에서 별도로 기록한다.

비교 시 다음 명령을 사용했다.

```bash
date '+%Y-%m-%d %H:%M:%S'
sudo -u agent-admin wc -l /var/log/agent-app/monitor.log
sudo -u agent-admin tail -n 3 /var/log/agent-app/monitor.log
```

| 구분 | 확인 시각 | 줄 수 | 마지막 로그 시각 |
| --- | --- | --- | --- |
| 기준 화면 | 2026-10-08 22:32:13 | 20 | 22:32:02 |
| 약 1분 후 | 2026-10-08 22:33:10 | 21 | 22:33:02 |

사용자가 수동 실행 없이 대기한 뒤 공유한 결과에서 새 기록과 줄 수 증가를 확인했다.

### 8.1 cron 등록·실행 주기를 변경하는 방법

아래는 기존 작업을 보존하면서 agent-admin의 모니터 실행 주기를 등록·변경하는 절차다. 이번 과제의 최종 주기는 매분이며, 다른 주기 예시는 변경 방법을 이해하기 위한 것이다.

#### 단계 1: 대상 계정의 기존 작업 확인과 백업

```bash

systemctl is-active cron
```

`-u agent-admin`은 그 계정의 예약 작업을 지정한다. 이를 빼면 다른 계정의 crontab을 편집할 수 있으므로 실행 계정을 확인한다. 이 실습에서는 기존 crontab이 있는 상태에서 백업한다. 처음 등록하는 환경에서 `no crontab for agent-admin`이 나오면 아직 작업이 없다는 뜻이다.

#### 단계 2: 편집기로 등록·변경

```bash
sudo crontab -u agent-admin -e
```

편집기 선택 화면이 나오면 nano를 선택한다. 기존의 `agent-app-monitor-managed` 줄이 있으면 그 줄을 수정하고, 없으면 아래 작업을 한 줄로 추가한다. 같은 모니터 작업을 중복 등록하지 않고 다른 예약 작업도 유지한다.

```cron
* * * * * /bin/bash /home/agent-admin/agent-app/bin/monitor.sh 2>&1 | /usr/bin/logger -t agent-monitor-study # agent-app-monitor-managed
```

nano에서는 `Ctrl+O` → Enter로 저장하고 `Ctrl+X`로 나온다. 사용자 crontab은 다섯 시간 필드 뒤에 실행 명령을 적으며, `agent-admin` 같은 사용자 이름 필드를 추가하지 않는다. 저장된 변경은 cron이 자동으로 읽으므로 매번 서비스를 재시작할 필요는 없다.

#### 단계 3: 시간 필드 이해와 주기 변경

```text
분  시  일  월  요일  실행할 명령
*   *   *   *   *     매분 실행
```

| 앞의 다섯 필드 | 실행 시점 |
|---|---|
| `* * * * *` | 매분 |
| `*/5 * * * *` | 매시간의 0·5·10…55분 |
| `*/10 * * * *` | 매시간의 0·10·20…50분 |
| `0 * * * *` | 매시간 정각 |
| `0 9 * * *` | 매일 오전 9시 |

예를 들어 5분 주기로 바꿀 때는 기존 줄의 앞부분만 다음처럼 바꾼다.

```cron
*/5 * * * * /bin/bash /home/agent-admin/agent-app/bin/monitor.sh 2>&1 | /usr/bin/logger -t agent-monitor-study # agent-app-monitor-managed
```

`*/5`는 저장한 순간부터 5분씩 기다리는 방식이 아니라 시계의 분 값이 0·5·10…일 때 실행하는 방식이다. 과제 제출 설정은 `* * * * *`로 유지한다. 시간 필드와 사용자 crontab 형식은 [Ubuntu 22.04 crontab 매뉴얼](https://manpages.ubuntu.com/manpages/jammy/man5/crontab.5.html)을 기준으로 설명했다.

#### 단계 4: 등록 내용과 자동 실행 결과 확인

```bash
sudo crontab -u agent-admin -l
date '+%Y-%m-%d %H:%M:%S'
sudo -u agent-admin wc -l /var/log/agent-app/monitor.log
sudo -u agent-admin tail -n 3 /var/log/agent-app/monitor.log
```

앱을 실행한 상태에서 모니터를 수동 실행하지 않고 다음 분이 지난 뒤 `date`, `wc`, `tail`을 다시 확인한다. 순환이 발생하지 않는 상황에서는 로그 줄 수가 증가하고 새 시각의 기록이 생겨야 한다. 앱이 중단되면 상태 점검에서 실패하므로 정상 자원 기록은 증가하지 않을 수 있다.

자동 실행 출력과 오류는 다음처럼 확인할 수 있다.

```bash
sudo journalctl -t agent-monitor-study --since '5 minutes ago' --no-pager
```

cron이 비활성 상태인 환경에서는 다음 명령으로 시작하고 자동 시작을 설정한다.

```bash
sudo systemctl enable --now cron
```

**실행 환경:** cron은 대화형 터미널의 환경 변수를 그대로 받지 않는다. 이 스크립트는 내부에서 PATH를 지정하고 `agent-env.sh`를 읽으며, crontab에는 Bash와 스크립트의 절대 경로를 사용한다. WSL 배포판과 cron이 실행 중이어야 예약 작업도 실행된다. WSL이 종료된 동안에도 계속 실행된다고 가정하지 않는다.

**출력 처리:** `2>&1`은 오류와 일반 출력을 합쳐 logger에 전달한다. `monitor.log`의 자원 기록은 스크립트가 별도로 작성한다. logger의 성공 여부와 모니터 자체의 종료 코드 0/1은 구분한다.

## 9. 필수 로그 용량 관리

### 9.1 적용 정책

- 용량 기준: 10 × 1024 × 1024 = 10,485,760바이트(10MiB).
- 새 줄과 줄바꿈을 추가했을 때 기준을 초과하면 먼저 순환한다.
- 가장 오래된 `monitor.log.9`를 삭제한다.
- 기존 `.8`부터 `.1`까지 역순으로 한 번호씩 이동한다.
- 현재 로그를 `monitor.log.1`로 이동한다.
- 새로운 현재 파일에 `>>`로 기록한다.
- 현재 로그와 백업 9개, 총 10개를 유지한다.

현재 로그가 이미 기준 크기 이하이고 정상적으로 순환이 수행되는 운영 상태에서, 관리 대상 로그의 내용 크기는 최대 약 100MiB로 제한된다. 이 정책은 `monitor.log`와 해당 백업에 적용되며, 앱 자체 로그나 시스템 저널 전체의 용량 정책은 아니다.

### 9.2 임시 파일을 이용한 검증

실제 운영 로그를 크게 만들지 않고, 임시 폴더의 LOG_FILE을 대상으로 기존 write_log 함수를 호출했다.

```bash
sudo -iu agent-admin /bin/bash <<'BASH'
set -e
source /home/agent-admin/agent-app/bin/monitor.sh

rotation_dir=$(mktemp -d /tmp/agent-rotation-test.XXXXXX)
LOG_FILE="$rotation_dir/monitor.log"

for n in {1..9}; do
  printf 'backup-%s\n' "$n" > "$LOG_FILE.$n"
done

truncate -s $((10*1024*1024)) "$LOG_FILE"
write_log "rotation-test"

stat -c '%n : %s bytes' "$LOG_FILE" "$LOG_FILE".[1-9]

file_count=$(find "$rotation_dir" -type f -name 'monitor.log*' | wc -l)
echo "로그 파일 수: $file_count"
test "$file_count" -eq 10
test "$(cat "$LOG_FILE.9")" = "backup-8"

echo "새 현재 로그:"
cat "$LOG_FILE"
echo "[PASS] 용량 기준 순환과 최대 10개 유지 확인"
BASH
echo "테스트 종료 코드: $?"
```

| 확인 항목 | 결과 |
| --- | --- |
| 새 monitor.log | 14바이트, rotation-test 기록 |
| monitor.log.1 | 10,485,760바이트 |
| 파일 개수 | 10 |
| 가장 오래된 백업 처리 | 기존 backup-8이 .9로 이동한 검사 통과 |
| 계속 기록 가능 여부 | 새 현재 로그 생성·기록 성공 |
| 테스트 종료 코드 | 0 |

## 10. 평가 문항별 답변과 이해 포인트

이 과제는 리눅스에서 앱을 안전하게 실행하고, 정상 동작과 시스템 자원을 주기적으로 점검하며, 결과를 로그로 남기는 실습이다. 아래 답변은 실제 코드와 실습 결과를 기준으로 작성했다. 캡처는 답변을 뒷받침하는 증거이며, 이미지 없이도 설정과 구현 이유를 이해할 수 있도록 설명했다. 항목 5의 보너스는 수행하지 않았다.

### 10.1 항목 1: 요구사항과 실제 동작

#### 1-1. SSH 포트가 20022로 변경됐고, Root 원격 접속이 차단됐는가?

**답변:** SSH 포트를 20022로 변경하고 `PermitRootLogin no`로 Root의 직접 원격 로그인을 차단했습니다. `sshd -T`로 적용 설정을 확인했고, `ss`로 SSH가 실제로 20022에서 연결을 기다리는 것도 확인했습니다.

**이해 포인트:** SSH는 다른 컴퓨터에 암호화된 연결로 접속해 명령을 실행하는 방법이다. 포트는 서버에서 접속을 받는 번호다. Root는 시스템 전체를 관리하는 계정이다. PowerShell에서 `wsl`로 로컬 Ubuntu를 여는 동작은 SSH 접속과 다르다.

```bash
sudo /usr/sbin/sshd -t
sudo /usr/sbin/sshd -T | grep -E '^(port|permitrootlogin) '
sudo ss -ltnp | grep sshd
```

관찰 결과는 `port 20022`, `permitrootlogin no`, SSH의 20022 LISTEN이다. 설정 파일의 내용과 실제 실행 상태를 함께 확인했다.

#### 1-2. 방화벽이 활성화됐고 20022/tcp와 15034/tcp만 허용되는가?

**답변:** UFW를 활성화하고 들어오는 연결은 기본적으로 차단했습니다. SSH용 20022와 앱용 15034 TCP 포트만 예외로 허용했습니다. IPv4와 IPv6 규칙도 확인했습니다.

```bash
sudo ufw status verbose
```

확인 결과는 `Status: active`, 기본 수신 정책 `deny (incoming)`, 두 포트의 허용 규칙이다.

**이해 포인트:** 방화벽은 연결을 허용하거나 차단한다. 앱은 실제로 포트를 열고 연결을 받아 준다. 방화벽에서 허용해도 앱이 실행되지 않으면 서비스는 사용할 수 없다. 이 캡처는 리눅스 내부 방화벽 설정의 증거이며, 외부에서 WSL까지 접속되는지까지 검증한 것은 아니다.

#### 1-3. 계정과 그룹이 요구사항대로 구성됐는가?

**답변:** agent-admin, agent-dev, agent-test를 구성했습니다. agent-common에는 세 계정을 모두 넣고, agent-core에는 admin과 dev만 넣었습니다. 실제 접근 검사에서 test는 업로드 디렉토리에 접근할 수 있었지만 키와 로그 디렉토리에는 접근할 수 없었습니다.

| 계정 | agent-common | agent-core | 역할 |
|---|---|---|---|
| agent-admin | 포함 | 포함 | 앱 실행, 모니터 실행, cron |
| agent-dev | 포함 | 포함 | monitor.sh 관리 |
| agent-test | 포함 | 미포함 | 공용 업로드 영역 사용 |

```bash
id agent-admin
id agent-dev
id agent-test
getent group agent-common agent-core
```

**이해 포인트:** 그룹은 여러 계정에 같은 권한을 주는 단위다. 그룹 구성 확인과 실제 경로 접근 확인은 서로 다른 검사이며, 둘 다 수행했다.

#### 1-4. 앱이 Boot Sequence 5단계를 통과하고 Agent READY가 출력되는가?

**답변:** agent-admin으로 앱을 실행했고 계정, 환경 변수, 필수 파일, 포트 사용 가능 여부, 로그 쓰기 권한의 5단계가 모두 `[OK]`인 것을 확인했습니다. 처음 발생한 키 경로 오류는 앱이 요구한 디렉토리 경로로 변경해 해결했습니다.

```bash
export AGENT_KEY_PATH="$AGENT_HOME/api_keys"
```

**이해 포인트:** 환경 변수는 프로그램에 실행 설정을 전달하는 값이다. 실제 앱의 오류 메시지는 키 파일 경로가 아니라 키 디렉토리 경로를 요구했다. 시작 검사에서 포트가 사용 가능하다는 것은 앱이 그 포트를 사용할 수 있다는 뜻이며, 시작 후의 LISTEN 상태는 별도로 확인했다.

**증거 상태:** 제출 캡처는 Boot 5단계 `[OK]`를 보여 준다. `Agent READY` 문구는 화면에 잘려 있으므로, 그 문구가 보이는 캡처는 추가해야 한다. 기존 자료만으로 해당 문구의 증거가 완료됐다고 설명하지 않는다.

#### 1-5. monitor.sh가 프로세스와 포트를 점검하고 비정상 상태에서 exit 1로 종료되는가?

**답변:** 앱 PID를 찾고, 15034 TCP 포트가 LISTEN 상태인지 확인하며, 포트를 소유한 PID가 앱 PID와 일치하는지도 검사합니다. 정상 실행은 종료 코드 0이었고, 실제 앱 중단 후 실행은 오류 메시지와 종료 코드 1이었습니다.

```bash
sudo -iu agent-admin /home/agent-admin/agent-app/bin/monitor.sh
echo "종료 코드: $?"
```

**이해 포인트:** PID는 프로세스 번호다. 종료 코드는 실행 결과를 다른 프로그램에 전달하는 값이다. 화면에 오류를 쓰는 것과 실패 코드 1을 반환하는 것은 별개의 동작이다. 실제 중단 테스트는 프로세스 부재 조건을 검증했고, 포트 부재와 소유 PID 불일치 조건은 코드에 구현돼 있다.

#### 1-6. monitor.log가 지정 형식으로 누적 기록되는가?

**답변:** 정상 점검 결과를 `/var/log/agent-app/monitor.log`에 시간, PID, CPU, 메모리, 디스크 사용률 순서로 기록합니다. `>>`로 기존 기록을 유지하면서 새 기록을 추가합니다.

```text
[2026-10-08 22:33:02] PID:4185,4186 CPU:1.2% MEM:5.6% DISK_USED:7%
```

```bash
sudo -u agent-admin tail -n 5 /var/log/agent-app/monitor.log
```

**이해 포인트:** 이 파일에는 정상 상태 점검을 통과하고 자원 측정까지 완료한 기록이 들어간다. 앱 프로세스가 없으면 그 전에 종료하므로 실패 메시지는 표준 오류로 출력된다. cron의 실행 출력과 오류는 logger로 전달하도록 등록했다.

#### 1-7. cron 매분 실행으로 monitor.log가 자동 증가하는가?

**답변:** agent-admin의 crontab에 매분 실행을 등록했습니다. 직접 모니터를 실행하지 않고 다음 분에 다시 확인했을 때, 로그가 20줄에서 21줄로 증가하고 새 기록이 생겼습니다.

```cron
* * * * * /bin/bash /home/agent-admin/agent-app/bin/monitor.sh 2>&1 | /usr/bin/logger -t agent-monitor-study # agent-app-monitor-managed
```

```bash
sudo crontab -u agent-admin -l
date '+%Y-%m-%d %H:%M:%S'
sudo -u agent-admin wc -l /var/log/agent-app/monitor.log
sudo -u agent-admin tail -n 3 /var/log/agent-app/monitor.log
```

**이해 포인트:** cron은 정해진 시간에 명령을 실행하는 도구다. 앞의 별 다섯 개는 매분 실행을 뜻한다. 22:32:13 확인 시 20줄이었고, 22:33:10에는 21줄과 22:33:02의 새 기록을 확인했다. 자동 실행 설정과 결과를 함께 확인했다. 파이프 끝의 logger 종료 코드가 monitor.sh의 종료 코드를 그대로 나타내는 것은 아니므로, 모니터의 0/1 검사는 직접 실행으로 수행했다.

#### 1-8. 로그 용량 관리 10MB/10개가 설정돼 있고 동작을 설명할 수 있는가?

**답변:** 코드 기준은 10MiB, 즉 10,485,760바이트입니다. 새 줄을 추가하면 이 크기를 초과하는 경우 기록 전에 로그를 순환합니다. 현재 로그와 백업 9개를 합쳐 최대 10개를 유지합니다. 임시 디렉토리에서 크기 초과와 백업 순환, 파일 수 10개 유지를 확인했습니다.

**이해 포인트:** 임시 현재 로그는 10,485,760바이트였고, 순환 후 `.1`로 이동했다. 새 현재 로그에는 `rotation-test`가 기록돼 14바이트가 됐다. 오래된 백업이 밀리고 총 파일 수가 10개인 것도 검사했다. 정상 운용에서 이 정책은 monitor.log 계열을 약 100MiB 이내로 관리하며, 앱 로그와 시스템 로그 전체의 크기를 제한하지는 않는다. 용량 관리 자체는 필수 과제다.

### 10.2 항목 2: 구현 방법과 선택 이유

#### 2-1. 프로세스 식별과 포트 확인에 사용한 명령과 선택 이유는?

**답변:** 프로세스 식별에는 `pgrep -f -x`를 사용했습니다. 설정한 앱 실행 명령행에 정확히 맞는 PID를 얻기 위해서입니다. 포트 확인에는 `ss -H -ltnp`를 사용해 TCP LISTEN과 소유 PID를 함께 확인했습니다. 앱 PID와 포트 소유 PID를 비교해 다른 프로그램이 해당 포트를 사용하는 상황도 구분합니다.

```bash
pgrep -f -x -- "$AGENT_APP_PATH"
ss -H -ltnp "sport = :$AGENT_PORT"
```

| 옵션 | 의미 |
|---|---|
| pgrep `-f` | 전체 명령행으로 검색 |
| pgrep `-x` | 전체 문자열이 일치하는 경우 선택 |
| ss `-H` | 표 머리글 제외 |
| ss `-l` | LISTEN 소켓 확인 |
| ss `-t` | TCP 확인 |
| ss `-n` | 주소와 포트를 숫자로 표시 |
| ss `-p` | 소유 프로세스 정보 확인 |

**이해 포인트:** 현재 식별 조건은 앱을 설정한 절대 경로로 실행하는 방식에 맞춰져 있다. 실행 인자를 추가하거나 실행 명령행이 달라지면 조건도 조정해야 한다. 같은 계정으로 앱과 모니터를 실행해 포트 소유 PID를 확인할 수 있게 했다.

#### 2-2. CPU·MEM·DISK 값을 어떻게 추출했고 로그 형식을 왜 고정했는가?

**답변:** CPU는 `/proc/stat`을 1초 간격으로 읽고 누적 시간의 차이로 계산했습니다. 메모리는 `/proc/meminfo`의 MemTotal과 MemAvailable로 계산했습니다. 디스크는 `df -P /`에서 사용률을 추출했습니다. 로그의 필드 이름과 순서를 고정해 기록 비교와 후속 값 추출을 쉽게 했습니다.

```text
CPU = (전체 시간 증가량 − 유휴 시간 증가량) / 전체 시간 증가량 × 100
MEM = (MemTotal − MemAvailable) / MemTotal × 100
DISK = 루트 파일시스템의 사용률
```

**이해 포인트:** CPU 값은 누적 시간이므로 두 시점의 차이를 계산해야 최근 구간의 사용률을 알 수 있다. 이 구현은 idle과 iowait를 유휴 시간으로 취급하며, guest 시간은 중복 합산하지 않는다. MemAvailable은 캐시 등 재사용 가능한 메모리도 고려한 추정치다. `df -P`는 일정한 출력 형식으로 사용률 열을 추출하기 위한 선택이다. `LC_ALL=C`도 설정해 출력 언어 차이를 줄였다. 측정한 것은 앱 하나가 아니라 리눅스 시스템 전체 자원이며, 디스크는 Windows 전체 드라이브가 아니라 `/` 파일시스템 기준이다.

#### 2-3. 소유자 agent-dev와 실행자 agent-admin·cron의 권한을 어떻게 만족시켰는가?

**답변:** 운영 monitor.sh의 소유자는 agent-dev, 그룹은 agent-core이며 권한은 750입니다. dev는 수정할 수 있고, core 그룹의 admin은 읽고 실행할 수 있습니다. cron도 admin으로 실행합니다. 로그 디렉토리는 admin이 기록할 수 있게 구성했습니다.

| 권한 대상 | 750의 의미 |
|---|---|
| 소유자 agent-dev | rwx: 읽기·쓰기·실행 |
| 그룹 agent-core | r-x: 읽기·실행 |
| 그 외 | ---: 권한 없음 |

```bash
sudo ls -l /home/agent-admin/agent-app/bin/monitor.sh
sudo -l -U agent-admin
```

**이해 포인트:** 운영 원본과 제출 복사본의 권한은 구분한다. 운영 원본은 750이고, skgun00이 만든 제출 복사본은 644였다. 방화벽 조회를 위해 admin에게 허용한 sudo 명령은 `/usr/sbin/ufw status` 하나다. 모니터는 `sudo -n`을 사용해 cron 실행 중 비밀번호 입력을 기다리지 않는다. 로그 디렉토리의 setgid는 새 파일의 그룹을 유지하도록 돕고, 기본 ACL과 `umask 0007`은 core 그룹 접근과 다른 사용자 차단을 유지하도록 구성했다.

#### 2-4. 용량 기반 로그 관리를 어떤 방식으로 구현했는가?

**답변:** logrotate 대신 스크립트의 `write_log` 함수로 구현했습니다. 현재 크기와 추가할 줄의 크기를 더해 기준 초과 여부를 확인합니다. 초과하면 오래된 `.9`를 삭제하고, `.8`부터 뒤 번호로 이동한 뒤 현재 로그를 `.1`로 바꿉니다. 이후 새 현재 로그에 기록합니다.

```text
.9 삭제 → .8을 .9로 이동 → … → .1을 .2로 이동
현재 monitor.log를 .1로 이동 → 새 monitor.log 작성
```

**이해 포인트:** 큰 번호부터 이동해야 기존 백업을 덮어쓰지 않는다. `.1`은 가장 최근 백업이고 `.9`는 가장 오래된 백업이다. `flock`으로 동시에 두 모니터가 기록하거나 순환하는 것을 막았다. 잠금을 얻지 못한 실행은 중복 점검을 건너뛰고 종료한다. 임시 로그를 이용한 테스트는 함수의 동작을 검증한 것이며, 실제 운영 로그를 테스트 데이터로 바꾸지 않았다.

### 10.3 항목 3: 설계 이유

#### 3-1. SSH 포트 변경과 Root 접속 차단이 보안에 효과적인 이유는?

**답변:** 기본 포트 22를 대상으로 하는 단순 자동 접속 시도를 줄이기 위해 포트를 변경했습니다. 변경한 포트도 스캔으로 찾을 수 있으므로 보조 조치입니다. Root는 시스템 전체를 변경할 수 있어 탈취 시 피해가 크기 때문에 직접 원격 로그인을 막고, 일반 계정에서 필요한 작업에만 sudo를 사용하도록 했습니다.

**이해 포인트:** 예상 위협은 자동 접속 시도와 계정 탈취다. 포트 변경이 인증 보안을 대신하지는 않는다. Root 직접 접속 차단은 가장 강한 계정으로 바로 진입하는 경로를 제한한다.

#### 3-2. api_keys와 로그 디렉토리를 agent-core로 제한한 이유는?

**답변:** 키에는 인증 정보가 있고 로그에는 운영 정보가 있어 노출이나 변조를 제한해야 합니다. 테스트 계정은 공용 업로드 작업만 필요하므로 키와 로그 접근 권한을 주지 않았습니다. 업무에 필요한 권한만 주는 최소 권한 원칙을 적용했습니다.

**이해 포인트:** 최소 권한은 모두에게 권한을 주고 사용하지 않기를 기대하는 방식이 아니라, 필요 없는 접근을 권한으로 차단하는 것이다. 상위 홈의 common 그룹 `--x` ACL은 필요한 하위 경로까지 통과할 수 있도록 부여한 권한이다. 홈의 모든 파일을 읽거나 목록을 볼 수 있다는 뜻은 아니다. 실제 계정별 접근 검사에서도 test의 키·로그 접근은 거부됐다.

#### 3-3. 방화벽 비활성·임계치 초과를 경고만 하고 종료하지 않는 이유는?

**답변:** 앱 프로세스나 서비스 포트가 없으면 핵심 상태 점검이 실패하므로 종료 코드 1로 끝냅니다. 자원 사용률 초과나 방화벽 비활성은 경고하고 나머지 점검을 계속합니다. 경고만으로 중단하면 다른 자원 상태와 로그 기록까지 놓칠 수 있기 때문입니다.

**이해 포인트:** CPU 20%, MEM 10%, DISK 80%를 초과할 때 경고하며, 같은 값일 때는 경고하지 않는다. 테스트에서는 CPU 21%, MEM 11%, DISK 81%를 함수에 전달하고 UFW 조회 함수의 응답을 inactive로 바꿨다. 경고 네 개와 계속 실행, 종료 코드 0을 확인했다. 실제 방화벽을 끄거나 과도한 시스템 부하를 만든 것은 아니다. 방화벽 경고가 중요하지 않다는 뜻도 아니다.

#### 3-4. `>`와 `>>`의 차이와 로그에 `>>`가 필요한 이유는?

**답변:** `>`는 기존 파일을 덮어쓰고, `>>`는 기존 내용 뒤에 추가합니다. 모니터링에서는 이전 상태와 장애 전후를 비교해야 하므로 `>>`로 기록을 누적했습니다. 누적으로 증가하는 용량은 로그 순환으로 관리했습니다.

```bash
# 아래는 기호 차이를 설명하는 예시이며 운영 로그 변경 명령이 아니다.
printf '첫 기록\n' > example.log
printf '다음 기록\n' >> example.log
```

**이해 포인트:** 운영 로그에 매번 `>`를 쓰면 최신 기록만 남아 시간에 따른 상태 변화와 장애 직전 기록을 잃는다.

### 10.4 항목 4: 상황 변화와 장애 대응

#### 4-1. 모니터링 대상이 Nginx로 바뀐다면 무엇을 수정해야 하는가?

**답변:** Nginx의 master·worker 구조와 실제 실행 방식에 맞춰 프로세스 식별 조건을 수정하겠습니다. 서비스 포트, 포트 소유 관계, 로그 경로와 접근 권한을 확인하고 임계값도 운영 환경에 맞게 조정하겠습니다. 웹 서비스의 응답까지 확인하려면 HTTP 상태 코드 등을 검사하는 방법도 추가할 수 있습니다.

**이해 포인트:** 실행 파일 이름만 바꾸면 충분한 것이 아니다. 명령행 형태와 프로세스 구조, 권한이 다를 수 있다. 현재 측정하는 CPU·메모리는 시스템 전체 값이므로 측정 목적도 구분해야 한다. TCP LISTEN은 연결을 받을 준비가 됐다는 증거이며, 웹 페이지의 정상 응답까지 보장하지는 않는다. 이번 과제에서 Nginx 전환을 구현한 것은 아니다.

#### 4-2. 프로세스는 살아 있는데 포트가 안 열리면 원인과 확인 순서는?

**답변:** 초기화 지연·실패, 잘못된 포트 설정, 다른 프로세스의 포트 점유, bind 권한 문제 등을 확인하겠습니다. 프로세스 존재만으로 앱이 서비스 준비를 마쳤다고 판단하지 않겠습니다.

1. 실제 실행 명령과 프로세스 상태를 확인한다.
2. `ss`로 LISTEN 주소·포트와 소유 PID를 확인한다.
3. 앱 로그에서 초기화 실패, 설정 오류, bind 실패를 확인한다.
4. 환경 변수·포트 점유·권한을 확인한다.
5. 로컬 LISTEN이 정상인데 외부 접속만 실패할 때 방화벽과 WSL 네트워크 경로를 확인한다.

**이해 포인트:** 방화벽의 연결 차단과 앱이 LISTEN 소켓을 만들지 못한 상황은 다르다. 방화벽 허용만으로 앱의 초기화 실패나 포트 충돌을 해결할 수는 없다.

#### 4-3. 로그 급증으로 디스크가 찰 위험이 있다면 단기·중기 대응은?

**답변:** 단기적으로 디스크 사용량과 커지는 로그 파일을 확인하겠습니다. 필요한 장애 증거를 보존한 뒤 오래된 기록을 정리하거나 불필요한 출력을 줄이겠습니다. 중기적으로 로그 순환의 실제 동작과 다른 앱·시스템 로그의 관리 정책을 점검하고, 디스크 사용량 감시와 적정 로그 수준을 적용하겠습니다.

**이해 포인트:** 무조건 모든 로그를 지우면 장애 원인 분석에 필요한 증거를 잃는다. 현재 용량 관리는 monitor.log에만 적용되므로 다른 로그가 디스크를 채울 수 있다. 이 답변은 운영 대응 방법에 대한 설명이며, 보너스의 기간별 압축·삭제 기능을 구현한 것은 아니다.

## 부록. monitor.sh 전체 소스

아래 소스는 사용자가 공유한 기존 monitor.sh에서 추출했다. 별도 제출 파일 `monitor.sh`에도 동일한 내용이 들어 있다. 사용자 실습 환경에서 관찰한 5,932바이트와 추출 파일 크기가 일치한다. 원격 원본과의 해시 비교는 수행하지 않았다.

공용 `agent-env.sh`의 최종 설정은 5.1절에 기록했다. 모니터는 운영 경로의 해당 설정 파일을 읽는다. 별도 monitor.sh를 다른 디렉토리에서 실행하는 경우에도 기본값은 운영 경로를 기준으로 하므로, 제출 파일만 옮기는 것이 전체 실습 환경 배포를 의미하지는 않는다.

```bash
#!/usr/bin/env bash
# 필수 과제: 상태 확인 → 자원 수집 → 경고 → 로그 기록/회전.

error() { printf '[ERROR] %s\n' "$*" >&2; }

# 제공 바이너리는 run-app.sh가 절대 경로로 실행한다.
# -f: 명령행 전체, -x: 전체 일치. 검색 명령 자체를 앱으로 오인하지 않는다.
find_app_pids() { pgrep -f -x -- "$AGENT_APP_PATH"; }
list_app_port() { ss -H -ltnp "sport = :$AGENT_PORT"; }

health_check() {
    local pids listeners pid matched=0
    pids=$(find_app_pids) || { error 'App process is not running.'; return 1; }
    [[ -n $pids ]] || { error 'App process is not running.'; return 1; }
    listeners=$(list_app_port) || { error 'Cannot inspect TCP sockets.'; return 1; }
    [[ -n $listeners ]] || { error "TCP $AGENT_PORT is not LISTENING."; return 1; }
    # 다른 프로그램이 같은 포트를 차지한 경우도 성공으로 처리하지 않는다.
    for pid in $pids; do
        [[ $listeners != *"pid=$pid,"* ]] || matched=1
    done
    (( matched )) || { error "TCP $AGENT_PORT is not owned by the app (or its PID is unreadable)."; return 1; }
    APP_PIDS=${pids//$'\n'/,}
    printf '[OK] Process PID:%s\n[OK] TCP %s LISTEN\n' "$APP_PIDS" "$AGENT_PORT"
}

ufw_status() { sudo -n /usr/sbin/ufw status; }

check_firewall() {
    local status
    if ! status=$(ufw_status 2>&1); then
        printf '[WARNING] Cannot query UFW; check the read-only sudo rule.\n'
    elif [[ $status == *'Status: active'* ]]; then
        printf '[OK] Firewall active (UFW)\n'
    else
        printf '[WARNING] Firewall inactive (UFW)\n'
    fi
    # 방화벽 경고는 치명적 오류가 아니다.
    return 0
}

read_cpu_counters() {
    # user, nice, system, idle, iowait, irq, softirq, steal만 합산.
    # guest 항목은 user 등에 이미 들어 있어 중복 합산하지 않는다.
    awk '/^cpu / {for(i=2;i<=9;i++) total+=$i; printf "%.0f %.0f\n",total,$5+$6; exit}' /proc/stat
}

cpu_from_counters() {
    # 두 시점의 누적값 차이로 1초 구간의 사용률을 구한다.
    awk -v total="$(($3-$1))" -v idle="$(($4-$2))" 'BEGIN {
        if(total<=0 || idle<0 || idle>total) exit 1
        printf "%.1f\n",100*(total-idle)/total
    }'
}

cpu_usage() {
    local total1 idle1 total2 idle2
    read -r total1 idle1 < <(read_cpu_counters) || return 1
    sleep 1
    read -r total2 idle2 < <(read_cpu_counters) || return 1
    cpu_from_counters "$total1" "$idle1" "$total2" "$idle2"
}

memory_usage() {
    awk '/^MemTotal:/ {t=$2} /^MemAvailable:/ {a=$2; found=1}
        END {if(t<=0 || !found || a<0 || a>t) exit 1; printf "%.1f\n",100*(t-a)/t}' /proc/meminfo
}

disk_usage() { df -P / | awk 'NR==2 {gsub(/%/,"",$5); print $5}'; }

warn_if_over() {
    if awk -v value="$2" -v limit="$3" 'BEGIN {exit !(value>limit)}'; then
        printf '[WARNING] %s %s%% > %s%%\n' "$1" "$2" "$3"
    fi
    return 0
}

write_log() {
    local line=$1 size=0 i
    local max_bytes=$((10*1024*1024))
    [[ ! -L $LOG_FILE ]] || { error 'Log must not be a symbolic link.'; return 1; }
    if [[ -e $LOG_FILE ]]; then
        [[ -f $LOG_FILE ]] || return 1
        size=$(stat -c %s -- "$LOG_FILE") || return 1
    fi
    # 새 줄을 더했을 때 10MiB를 초과하면 먼저 회전한다.
    if (( size + ${#line} + 1 > max_bytes )); then
        rm -f -- "$LOG_FILE.9" || return 1
        for ((i=8;i>=1;i--)); do
            if [[ -e $LOG_FILE.$i ]]; then
                mv -- "$LOG_FILE.$i" "$LOG_FILE.$((i+1))" || return 1
            fi
        done
        mv -- "$LOG_FILE" "$LOG_FILE.1" || return 1
    fi
    # 현재 로그 + .1~.9 = 총 10개. .1이 가장 최근의 백업이다.
    printf '%s\n' "$line" >> "$LOG_FILE" || return 1
}

main() (
    set -euo pipefail
    export LC_ALL=C PATH=/usr/sbin:/usr/bin:/sbin:/bin
    umask 0007
    local script_dir config tool cpu mem disk value
    script_dir=$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)
    config=$script_dir/../agent-env.sh
    [[ ! -r $script_dir/agent-env.sh ]] || config=$script_dir/agent-env.sh
    if [[ -r $config ]]; then source "$config"; fi
    AGENT_HOME=${AGENT_HOME:-/home/agent-admin/agent-app}
    AGENT_APP_PATH=${AGENT_APP_PATH:-$AGENT_HOME/agent-app-linux-x86}
    AGENT_PORT=${AGENT_PORT:-15034}
    AGENT_LOG_DIR=${AGENT_LOG_DIR:-/var/log/agent-app}
    LOG_FILE=$AGENT_LOG_DIR/monitor.log
    [[ $(uname -s) == Linux ]] || { error 'Linux is required.'; return 1; }
    for tool in pgrep ss awk df stat flock date; do
        command -v "$tool" >/dev/null || { error "Missing command: $tool"; return 1; }
    done
    [[ -d $AGENT_LOG_DIR && -w $AGENT_LOG_DIR ]] || { error 'Log directory is not writable.'; return 1; }
    [[ ! -L $AGENT_LOG_DIR/.monitor.lock ]] || return 1
    exec 9>> "$AGENT_LOG_DIR/.monitor.lock"
    if ! flock -n 9; then echo '[INFO] Another monitor is running; skipped.'; return 0; fi

    printf '====== SYSTEM MONITOR RESULT ======\n[HEALTH CHECK]\n'
    health_check || return 1
    check_firewall
    cpu=$(cpu_usage) || { error 'Cannot measure CPU.'; return 1; }
    mem=$(memory_usage) || { error 'Cannot measure memory.'; return 1; }
    disk=$(disk_usage) || { error 'Cannot measure root filesystem.'; return 1; }
    for value in "$cpu" "$mem" "$disk"; do
        [[ $value =~ ^[0-9]+([.][0-9]+)?$ ]] || { error 'Invalid measurement.'; return 1; }
    done
    printf '[RESOURCES]\nCPU: %s%%\nMEM: %s%%\nDISK_USED: %s%%\n' "$cpu" "$mem" "$disk"
    warn_if_over CPU "$cpu" 20
    warn_if_over MEM "$mem" 10
    warn_if_over DISK_USED "$disk" 80
    write_log "[$(date '+%Y-%m-%d %H:%M:%S')] PID:$APP_PIDS CPU:$cpu% MEM:$mem% DISK_USED:$disk%" || {
        error 'Cannot write or rotate monitor.log.'; return 1;
    }
    printf '[INFO] Log appended: %s\n' "$LOG_FILE"
)

# source로 읽을 때는 함수만 정의하고, 직접 실행할 때만 main을 호출한다.
if [[ ${BASH_SOURCE[0]} == "$0" ]]; then main "$@"; fi
```
