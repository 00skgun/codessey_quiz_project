01. 사용한 기술 구분

Vercel = 프로그램 실행·배포
챗봇을 인터넷에서 실행하는 플랫폼. 서버리스는 서버가 없다는 뜻이 아니라 서버 관리를 제공자에게 맡긴다는 뜻.
Neon = DB 제공·운영 서비스
우리 PostgreSQL DB를 제공하는 서비스. 사용자와 대화 기록은 여기서 보관한다.
PostgreSQL = DB 시스템
실제로 데이터를 저장·조회하고 제약조건과 트랜잭션을 관리한다.
SQLAlchemy = Python 라이브러리
Python에서 DB를 다루는 도구. 객체와 테이블을 연결하는 ORM 기능을 사용한다. DB 자체가 아니다.
psycopg = PostgreSQL 드라이버
SQLAlchemy가 PostgreSQL과 실제로 통신할 때 사용하는 드라이버.

왜 Vercel + Neon인가?

앱 실행·배포와 데이터 보관을 분리한다. 서버리스의 로컬 파일은 영구 저장과 실행 환경 간 공유를 보장할 수 없으므로, 같은 외부 DB에 접근하도록 구성했다.

SQLite 자체가 저장을 못 한다는 뜻은 아니다. 우리 배포 환경에서 쓰기 가능한 영구 파일 DB로 운영하기 어렵다는 것이다.

선택의 단점: 네트워크와 외부 서비스 장애에 영향을 받는다. 배포는 D 담당이며, 플랫폼 선택은 팀 구성에 따른 설명이다.

02. 파일별 역할

database.py — 연결 준비
DATABASE_URL 읽기, Engine·SessionLocal 설정, 공통 Base 정의. 테이블을 자동 생성하는 파일은 아니다.
models.py — 저장 구조
네 담당은 ChatLog. 컬럼·자료형·외래키·제약조건·인덱스를 정의한다. User 모델은 A 담당.
crud.py — 저장·조회
전달받은 값으로 객체를 만들어 저장하거나 DB에서 조회한다. 현재 수정·삭제 전용 함수는 없다.
routers/logs.py — 조회 API
인증된 사용자의 요청을 받아 조회 함수를 호출하고 결과를 응답 형식으로 변환한다.
schemas.py — API 데이터 형식
D 담당. 너는 ChatLogItem 같은 공통 응답 모델을 가져다 사용한다.
docs/ERD.md — 구조 설명 문서
사람이 읽는 설명서. 프로그램이 이 문서를 읽어서 테이블을 만드는 것이 아니다.
scripts/create_tables.py — 초기화
없는 users·chat_logs 테이블을 수동으로 생성한다.
scripts/check_logs.sql — 검증
테이블 구조와 저장된 데이터를 조회한다. 데이터 수정·삭제는 하지 않는다.

“연결 준비, 저장 구조, 실제 DB 작업, HTTP 요청 처리를 분리했습니다. 같은 함수를 재사용하고 수정·테스트할 위치를 명확하게 하기 위해서입니다.”

03. 대화가 저장되는 순서

  1. 인증으로 사용자를 확인한다.
  2. chat_service.py가 CRUD로 최근 성공 대화를 조회한다.
  3. AI를 호출해 답변을 받는다.
  4. create_chat_log()에 질문·답변·사용자 번호 등 값을 전달한다.
  5. CRUD 함수 안에서 ChatLog 객체를 만들고 저장·확정한다.
  6. 저장된 객체를 반환하고, 서비스가 답변과 chat_id로 성공 응답을 만든다.
# 메모리에 객체 생성
chat_log = ChatLog(...)

# 저장 대상으로 등록
db.add(chat_log)
# INSERT 실행, 아직 확정 전
db.flush()
# DB의 ID·시각 등을 읽기
db.refresh(chat_log)
# 저장 확정
db.commit()

return chat_log

ChatLog(...)만 만들면 Python 메모리에 있다. add만으로 저장이 확정되는 것도 아니다. 네 코드에서는 flush 때 INSERT가 실행된다.

SQLAlchemy가 psycopg를 통해 DB에 요청을 보낸다. 별도 flush를 생략해도 commit은 필요한 변경사항을 먼저 flush한다.

refresh는 “DB 수정”이 아니라 “DB 값을 다시 읽어 Python 객체에 반영”하는 작업이다.

“저장 확정 뒤 성공 응답을 반환해 화면과 DB 기록이 다르게 남는 일을 피했습니다. 저장 실패를 숨기면 다음 질문의 문맥에서도 이번 대화가 빠질 수 있습니다.”

04. 실패하면 rollback과 raise

except SQLAlchemyError:
    db.rollback()
    raise
SQLAlchemyError
SQLAlchemy 관련 오류의 기본 예외 클래스. 중복 아이디나 외래키 위반 같은 오류를 잡을 수 있다. 모든 Python 오류를 뜻하지는 않는다.
rollback()
아직 확정하지 않은 트랜잭션을 취소한다. flush로 실행한 새 INSERT도 commit 전이라면 취소된다. 별도로 DELETE할 필요가 없다.
raise
발생한 오류를 호출한 코드에 다시 전달한다. 실패했는데 성공한 것처럼 진행하지 않도록 한다.

이미 commit된 과거 기록은 이후 rollback으로 지워지지 않는다.

DB 연결이 끊긴 경우에는 rollback 자체도 실패할 수 있다. 모든 장애가 복구된다고 보장하는 장치는 아니다.

“rollback은 미확정 작업 취소, raise는 호출자에게 실패 전달입니다.”

05. Engine과 Session

Engine
접속 정보와 DB 연결을 관리하는 객체. 생성만으로 접속을 확인하거나 테이블을 만드는 것은 아니다.
SessionLocal
설정된 Session을 만들어주는 생성 도구.
db = SessionLocal()
도구를 호출해 실제 DB 작업용 Session 하나를 만든다. 이 db가 CRUD로 전달된다.
db = SessionLocal()
db.add(user)
db.commit()
db.close()

위는 역할 설명용 코드다. 실제 프로젝트에서는 deps.py의 get_db가 Session을 제공하고 finally에서 닫는다.

로그인 세션과는 다르다

  • 인증: 쿠키에 담긴 JWT를 검증한다.
  • DB 작업: SQLAlchemy Session을 사용한다.

설정의 뜻

pool_pre_ping=True
보관된 연결을 다시 쓰기 전에 살아 있는지 확인.
autoflush=False
조회 전 자동 flush를 끈다. commit에 필요한 flush까지 막지는 않는다.
expire_on_commit=False
commit 뒤에도 객체에 읽어둔 값을 유지. DB의 다른 변경을 자동 반영한다는 뜻은 아니다.
hide_parameters=True
SQLAlchemy 로그·오류 문자열에서 SQL 입력값을 숨기는 최신 보완 설정. 모든 로그의 모든 비밀값을 숨기지는 않는다.

06. 사용자와 대화를 나눈 이유

사용자 정보는 users에 한 번, 대화는 chat_logs에 여러 번 저장한다. 사용자 1명이 10번 대화하면 users는 1행, chat_logs는 10행이다.

chat_logs.id
질문·답변 또는 실패 결과를 담은 대화 기록 한 건의 고유 번호.
chat_logs.user_id
그 대화를 남긴 사용자 번호. 한 사용자의 여러 기록에서 반복될 수 있다.
request_id
어떤 요청을 처리하면서 생긴 기록인지 추적하는 식별자.

대화마다 이름과 비밀번호 해시까지 저장하면 중복이 생긴다. 비밀번호 변경 때 여러 행을 수정해야 하고, 일부만 바꾸면 불일치가 생길 수 있다.

사용자 정보를 분리하면 비밀번호 변경은 해당 users 행의 password_hash에만 반영하면 된다. 사용자 번호와 대화 기록은 그대로다.

비밀번호 변경은 구조를 설명하는 예시다. 현재 앱에 변경 기능이 구현되어 있다는 뜻은 아니다.

“사용자 정보의 중복을 줄이고, 한 사용자에게 여러 대화를 연결하기 위해 1:N으로 분리했습니다. 대화를 행별로 관리하면 최근 기록 선택·상태별 필터·페이지 조회도 직접적으로 표현할 수 있습니다.”

07. 외래키 ≠ 접근 권한

ForeignKey("users.id")

이 규칙은 대화에 적힌 사용자 번호가 users에 존재해야 한다는 뜻이다.

  • 99번 사용자가 없다 → user_id=99 저장 시 외래키 오류.
  • 99번 사용자가 있다 → 해당 외래키 조건 통과.

외래키는 현재 로그인한 사용자를 검사하거나 다른 사람의 기록을 숨겨주지 않는다.

# 인증된 사용자 번호를 전달
crud.list_chat_logs(db, user.id, ...)

# 그 사람의 기록만 선택
.where(ChatLog.user_id == user_id)

우리 기록 API는 요청의 임의 user_id를 조회 기준으로 받지 않는다. 로그인한 7번 사용자가 ?user_id=99를 붙여도 조회에는 인증된 7번을 사용한다.

“인증은 누구인지 확인하고, 조회 조건은 그 사람의 기록만 선택합니다. 외래키는 데이터 참조 관계를 보장할 뿐 접근 권한을 대신하지 않습니다.”

08. Mapped와 모델 읽기

question: Mapped[str] = mapped_column(Text)
  • question: 항목 이름
  • Mapped[str]: DB와 연결되는 문자열 속성
  • mapped_column(Text): DB의 텍스트 컬럼 정의
error_code: Mapped[str | None]

문자열 또는 값 없음(None)을 담는다는 타입 표시다.

매핑 = Python 객체의 속성과 DB 컬럼 연결. Python의 map() 함수와는 다른 이야기다. Base 상속과 테이블·컬럼 선언으로 매핑된다.

from app.models import ChatLog, User

CRUD가 모델의 정의를 가져오는 코드다. import 자체가 DB 데이터를 조회하는 것은 아니다. 실제 값은 객체 생성 시 전달하거나 DB 조회를 통해 채워진다.

09. CRUD 함수 6개

get_user_by_username()
로그인 아이디로 조회. 있으면 User, 없으면 None. 비밀번호 검증이나 로그인 완료를 뜻하지 않는다.
get_user_by_id()
사용자 기본키로 조회. 인증 코드가 토큰을 검증한 뒤 DB에도 사용자가 존재하는지 확인할 때 사용.
create_user()
아이디와 이미 해시된 비밀번호를 받아 사용자 저장. 직접 해싱하거나 해시 여부를 검사하지 않는다.
create_chat_log()
대화의 성공·실패 결과 저장. 성공 시 commit, DB 오류 시 rollback 후 raise.
recent_turns()
해당 사용자의 최근 성공 기록 최대 n개를 선택하고 과거 → 현재로 반환. AI 문맥용.
list_chat_logs()
해당 사용자의 성공·실패 기록을 최신순으로 반환. limit·offset으로 나누어 조회.

현재 수정(Update)·삭제(Delete) 전용 함수는 없다. 새 대화는 기존 행을 수정하지 않고 새 행으로 추가한다.

왜 CRUD를 따로 모았나?

같은 조회 함수를 채팅 화면·로그 화면·조회 API에서 재사용한다. 사용자 필터와 정렬을 반복 작성하지 않아도 되고, 한 곳에서 테스트·수정할 수 있다. 대신 파일을 오가며 읽고 함수 계약을 맞춰야 한다.

10. 최근 대화를 선택하는 순서

.where(
    ChatLog.user_id == user_id,
    ChatLog.status == "success",
)
.order_by(
    ChatLog.created_at.desc(),
    ChatLog.id.desc(),
)
.limit(n)

먼저 해당 사용자의 성공 기록만 필터링한다. 그 안에서 최신순으로 최대 n개를 선택하고, 조회한 목록을 reversed로 뒤집는다.

최신순:    44 → 43 → 42 → 41
2개 선택:  44 → 43
뒤집기:    43 → 44
  • n=5는 “반드시 5개”가 아니라 “최대 5개”.
  • 본인의 성공 기록이 3개면 3개만 반환한다.
  • 부족한 수를 다른 사용자의 대화로 채우지 않는다.
  • 시각이 같아도 순서를 확정하려고 id를 보조 정렬 기준으로 사용한다.
  • 조회 함수이므로 데이터 수정이나 저장 commit을 하지 않는다.

왜 최근 5개만?

전체 대화를 매번 보내면 입력 토큰과 처리 부담이 늘기 때문이다. 대신 오래된 내용을 놓칠 수 있다. 5는 조정 가능한 설정이며 정확한 토큰 상한을 보장하지 않는다.

왜 limit·offset으로 나누나?

기록 전체를 한꺼번에 전송하지 않고 필요한 분량만 읽기 위해서다. offset=20, limit=20이면 최신순 앞 20개를 건너뛰고 다음 최대 20개다.

단점: offset이 크면 조회 비용이 커질 수 있고, 새 데이터가 들어오면 경계가 밀릴 수 있다. 커서 방식이나 토큰 예산 검사는 추가 개선안이며 현재 구현했다고 말하면 안 된다.

11. 실패 기록도 남기는 이유

AI 실패를 정상 답변으로 처리하지는 않지만, 실패한 요청의 이력은 남길 수 있다.

answer = ""
status = "error"
error_code = "AI_TIMEOUT"
status
성공·실패 구분. 사용자 화면에는 둘 다 보여주고 AI 문맥에는 성공만 사용한다.
error_code
오류 종류. 상세 내부 원인 전체나 예외 원문을 담는 것은 아니다.
request_id
대화 기록과 같은 요청의 서버 로그를 연결한다.
latency_ms
AI 처리에 걸린 시간. 질문부터 브라우저 표시까지의 전체 시간을 뜻하지는 않는다.
provider·model
어떤 제공자·모델로 처리했는지 추적한다.

AI 실패와 DB 저장 실패는 별개다. AI가 실패해도 DB가 정상이면 실패 행을 저장할 수 있다. DB까지 장애면 실패 행도 남지 않을 수 있다.

예외 원문을 그대로 사용자에게 보여주면 SQL·입력값 등 내부 정보가 노출될 수 있으므로, 정해진 코드와 안전한 문구로 안내한다.

12. 기록 없음과 DB 장애는 다르다

사용자 한 명 조회: 없음
조회 성공. 반환값 None.
대화 목록 조회: 없음
조회 성공. 반환값 빈 리스트 [].
대화 목록 조회: 기록 있음
조회 성공. ChatLog 객체 목록 반환.
DB 조회 자체가 실패
예외 발생. GET /api/me/chats에서는 공통 INTERNAL_ERROR로 바꾸어 HTTP 500 응답.

""는 빈 문자열이고 []는 빈 목록이다.

“DB 장애를 빈 리스트로 숨기면 정상 조회로 오해합니다. 사용자는 기록이 없거나 사라졌다고 생각할 수 있어, 조회 실패를 별도 오류로 알립니다.”

13. API 응답 ≠ DB 전체 컬럼

ChatLog는 DB 모델이고, ChatLogItem은 API 응답 모델이다.

DB에는 11개 컬럼이 있다: id, user_id, request_id, question, answer, status, error_code, provider, model, latency_ms, created_at.

조회 API는 8개를 반환한다: chat_id, request_id, question, answer, status, error_code, latency_ms, created_at.

ChatLogItem.model_validate(log)

조회한 객체를 정해진 응답 형식으로 변환한다. JSON에 model이 없다는 것만으로 DB에 저장되지 않았다고 판단하면 안 된다.

@property
def chat_id(self) -> int:
    return self.id

chat_id는 기존 id를 읽는 별칭 속성이다. DB에 번호를 두 번 저장하는 별도 컬럼이 아니다.

14. 테이블 초기화는 언제?

python -m scripts.create_tables --confirm

담당자가 명령을 직접 실행할 때만 동작한다. 앱 시작·질문 전송·일반 Vercel 재배포 시 자동 실행되지 않는다.

  • 없는 users·chat_logs 테이블 → 생성.
  • 이미 있는 테이블 → 그대로 유지.
  • 기존 테이블의 컬럼 변경 → 자동 반영하지 않음.

create_all(checkfirst=True)는 최초 테이블 생성 도구이며 마이그레이션이 아니다. 구조 변경은 별도의 ALTER TABLE 또는 마이그레이션 절차가 필요하다.

--confirm은 명시적으로 실행하게 만드는 옵션이지, development인지 production인지 자동 검사하는 장치는 아니다.

“DB 구조 준비를 앱 실행과 분리했습니다. 담당자가 대상 DB를 확인한 뒤 명시적으로 초기화하기 위해서입니다.”

15. 환경변수와 테스트 격리

DATABASE_URL은 환경변수 이름(Key)이고, 실제 접속 문자열은 값(Value)이다. 접속 정보는 코드에 하드코딩하지 않는다.

  • 배포 앱: Vercel 프로젝트 환경변수.
  • 로컬 앱: .env 또는 실행 프로세스 환경변수.
  • 코드: os.environ.get("DATABASE_URL")로 읽음.

일반 앱이 .env를 읽는 것은 로컬 실행 명령의 --env-file 설정이다. create_tables.py는 .env를 자동으로 읽지 않는다.

개발·운영 분리의 한계

코드는 설정된 주소로 연결한다. 로컬 실행이어도 production 주소를 넣으면 운영 DB에 접근한다. 현재 database.py에는 production 연결 차단 검사가 없다.

실제 PostgreSQL 테스트는?

  • TEST_DATABASE_URL을 별도로 사용.
  • 없으면 해당 통합 테스트는 skip.
  • 앱의 DATABASE_URL로 대신 연결하지 않음.
  • 테스트마다 고유 스키마·트랜잭션으로 격리하고 정리.

잘못된 테스트 URL까지 자동 차단하는 것은 아니다. 운영 DB를 지정하지 않아야 한다.

왜 실제 DB 테스트도 했나?

가짜 객체 테스트는 호출 순서를 확인한다. 실제 PostgreSQL 테스트는 제약 위반과 rollback 후 같은 Session의 재사용 등 실제 DB 동작을 검증한다.

비밀번호를 Git에 올렸다면?

삭제 커밋만으로는 부족하다. 담당자에게 즉시 알리고 노출된 비밀번호를 교체해 기존 정보를 무효화한다. 앱 환경변수도 갱신하고 Git 이력·재발 방지를 정리한다.

16. 저장 확인과 역할 경계

실제 저장을 보여주는 방법

  1. 로그인해서 구별되는 질문을 보낸다.
  2. 같은 브라우저에서 /api/me/chats를 연다.
  3. 방금 보낸 question·answer·created_at·chat_id를 확인한다.
  4. 다른 계정에서는 그 기록이 나오지 않는지 확인한다.

API는 화면 내용을 다시 읽는 것이 아니라 DB를 다시 조회한다. scripts/check_logs.sql로도 검증할 수 있다.

정확한 담당 범위

A — 인증
User 모델, 비밀번호 해싱·검증, JWT, 로그인·로그아웃.
C — 최건영 / DB
DB 연결 기반, 사용자 저장·조회, ChatLog, 대화 저장·조회, 본인 기록 API, 초기화 도구·확인 SQL·관련 테스트.
B — AI
AI 호출과 대화 처리 흐름. CRUD 함수를 호출해 연결.
D — 앱·화면·배포
공통 스키마, 앱·화면 연결, 배포 환경변수 등록과 실제 Neon 초기화 실행.

password_hash라는 인자 이름만으로 해싱되지는 않는다. A가 해시한 값을 전달한다는 계약이며, 네 저장 함수는 해시 여부를 검사하지 않는다.

“인증 코드는 사용자를 확인하고, 대화 처리 코드는 질문과 AI 결과를 준비합니다. 저는 이를 저장·조회하는 DB 계층을 구현했습니다. 인증된 사용자 ID로 조회 범위를 제한하고, 저장 실패 시 rollback 후 오류를 전달합니다.”

17. 평가 전 셀프 질문

먼저 말로 답한 뒤 눌러서 확인하기.

1. database.py가 질문·답변을 전달하나요?

아니다. 연결·Session 기반을 준비한다. chat_service.py가 값을 create_chat_log()에 전달하고 CRUD가 저장한다.

2. ChatLog(...)만 만들면 어디에 있나요?

Python 메모리에 객체가 있다. 아직 DB 저장 확정이 아니다.

3. flush와 commit은 왜 나눴나요?

flush는 변경 SQL 실행, commit은 트랜잭션 확정이다. 네 코드는 flush 뒤 refresh로 생성값을 읽고 commit한다.

4. 외래키가 남의 기록을 숨기나요?

아니다. 참조하는 사용자의 존재를 보장한다. 본인 기록 조회는 인증된 ID와 WHERE 조건으로 제한한다.

5. 사용자 번호와 대화 번호가 왜 다른가요?

한 사용자에게 여러 대화가 연결되기 때문이다. user_id는 반복될 수 있지만 대화 기본키 id는 고유하다.

6. recent_turns에 성공 기록이 3개뿐이면?

3개만 반환한다. n=5는 최대 개수이며, 다른 사용자의 기록으로 채우지 않는다.

7. 44·43·42에서 2개를 고르고 뒤집으면?

44·43을 고른 뒤 43·44를 반환한다. 42를 다시 가져오지 않는다.

8. AI 실패를 왜 DB에 저장하나요?

사용자가 실패한 질문을 확인하고, 운영자가 오류 코드·요청 ID로 추적하기 위해서다. AI 문맥에서는 실패 기록을 제외한다.

9. DB 장애 때 []를 반환해도 되나요?

안 된다. “조회 성공, 기록 없음”으로 오해된다. 우리 조회 API는 실패를 공통 오류 응답으로 전달한다.

10. 왜 SQLAlchemy를 사용했나요?

Python 모델과 DB 테이블을 연결하고, Session으로 조회·저장과 트랜잭션을 관리하기 위해서다.

11. create_tables가 재배포 때 자동 실행되나요?

아니다. 별도의 수동 명령이다. 없는 테이블만 만들며 기존 구조 변경은 하지 않는다.

12. API에 model이 없으면 저장 누락인가요?

그렇게 판단할 수 없다. DB 저장 모델과 API 응답 모델이 다르다. 실제 저장값은 SQL 조회로 확인한다.

13. 평가표 최소 추적 필드는?

사용자=user_id, 시간=created_at, 질문=question, 응답=answer.

14. 비밀번호 해싱도 내 함수가 하나요?

아니다. A가 해싱하고 C의 create_user가 받은 값을 저장한다. 함수 자체는 해시 여부를 검사하지 않는다.
