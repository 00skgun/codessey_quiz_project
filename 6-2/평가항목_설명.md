# AI 도구 학습 평가항목 설명

첨부된 평가표의 항목 1~4에 대한 구현 설명과 시연 안내입니다. 항목 5 보너스는 수행하지 않습니다. 아래 답변은 현재 코드에 근거하며, 실제 API 실행 결과와 모의 API를 사용하는 자동 테스트를 구분했습니다.

## 먼저 설명할 프로젝트 개요

> 제가 만든 프로그램은 Git의 변경 내용을 읽고 AI API에 전달해서 커밋 메시지와 PR 초안을 생성하는 Python CLI입니다. 변경 수집, 민감정보 처리, 프롬프트 구성, API 호출, 응답 검증, 터미널 출력을 각각 함수로 분리했습니다. 생성된 설명은 사용자가 검토한 뒤 적용하며, 프로그램이 실제 커밋이나 PR을 자동으로 만들지는 않습니다.

흐름: `git status / git diff → prepare_context → make_messages → call_api → parse_output → render_output`

주요 파일은 `main.py`(프로그램), `test_main.py`(자동 검증), `README.md`(사용 안내)입니다.

## 항목 1. 기능 동작과 출력 확인

### 1-1. 프로젝트 루트에서 커밋 메시지가 출력되는가?

> Git 저장소 루트에서 `commit` 명령을 실행하면 변경 파일 목록과 staged/unstaged diff를 읽습니다. 이 내용을 AI에 전달한 뒤 제목과 선택적인 본문을 `--- Commit Message ---` 아래에 출력합니다. `--path 6-2`를 사용하면 같은 저장소의 다른 미션은 분석 대상에서 제외됩니다.

```powershell
cd C:\Users\user\Desktop\2026\codessey
py -3.12 .\6-2\main.py commit --path 6-2
```

사용자 실제 실행에서 `AI 커밋/PR 생성기 구현 및 경로 필터링 기능 추가`라는 제목과 변경 요약이 출력되었습니다. 신규 파일의 내용은 `git add` 후 diff에 포함됩니다. 커밋 완료 후 변경이 없는 상태에서는 새 초안 대신 변경 없음 메시지가 나오는 것이 정상입니다.

### 1-2. PR 제목과 본문 초안이 출력되는가?

> `pr` 명령은 PR용 JSON 구조를 요청합니다. 결과를 검사한 다음 제목은 `--- PR Title ---`, 본문은 `--- PR Body ---` 아래에 출력합니다. 이 명령은 GitHub에 실제 PR을 생성하지 않습니다.

```powershell
py -3.12 .\6-2\main.py pr --path 6-2
```

사용자가 공유한 실제 실행 결과로 PR 본문 생성이 확인됐습니다. 공유된 발췌에는 제목 부분이 없으므로 실 API 제목 출력 증빙은 전체 터미널 출력을 확인해야 합니다. 제목과 본문이 함께 출력되는 코드는 모의 API를 사용하는 통합 테스트로 검증합니다.

### 1-3. API 키가 없으면 오류를 출력하고 종료하는가?

> 분석할 변경이 있는데 `AI_API_KEY`가 설정되지 않았다면 `[ERROR] AI_API_KEY 환경변수가 설정되지 않았습니다.`를 출력하고 종료 코드 1로 종료합니다. API를 호출하지 않아 불필요한 요청도 발생하지 않습니다. URL과 모델 누락도 각각 구분해서 안내합니다.

이 동작은 `CLITests.test_missing_key_fails_without_request`에서 검증합니다. 변경 자체가 없는 경우에는 키 검사보다 먼저 변경 없음으로 종료합니다. 따라서 키 누락 시연은 diff가 있는 상태에서 해야 합니다.

키를 지우고 다시 입력하는 대신 다음 테스트로 오류 안내와 호출 차단을 함께 확인할 수 있습니다.

```powershell
cd C:\Users\user\Desktop\2026\codessey\6-2
py -3.12 -m unittest -v test_main.CLITests.test_missing_key_fails_without_request
```

### 1-4. 변경이 없으면 안내 메시지를 출력하는가?

> `git status` 결과가 비어 있으면 `[INFO] 변경 사항이 없습니다.`를 출력하고 종료 코드 0으로 끝납니다. 정상적인 무작업 상태이므로 오류로 취급하지 않으며 API도 호출하지 않습니다.

임시 Git 저장소에서 변경 없음, staged 변경, unstaged 변경을 검증하고, 별도 테스트에서 변경이 없을 때 API 호출이 0회인지 확인합니다. `--path 6-2` 사용 시 다른 미션에 변경이 있어도 `6-2`에 변경이 없으면 이 안내가 나옵니다.

### 1-5. Why / What / How to Test 및 불릿을 포함하는가?

> AI에게 `why`, `what`, `how_to_test` 배열을 요청하고, 각 배열에 비어 있지 않은 문장이 최소 1개 있는지 검사합니다. 그 후 프로그램이 정확한 섹션 제목과 `-` 불릿을 붙입니다. 필수 내용이 없으면 그럴듯한 문장을 임의로 채우지 않고 오류로 종료합니다.

- **Why**: 변경 배경과 이유. diff만으로 의도를 알 수 없으면 추정임을 표시하도록 요청합니다.
- **What**: 실제 변경 사항.
- **How to Test**: 사용자가 실행해 볼 검증 방법. AI가 실제 테스트를 실행했다고 주장하지 않도록 요청합니다.

### 1-6. temperature 또는 max-tokens를 바꾸면 차이가 재현되는가?

> CLI로 받은 값을 실제 요청 JSON에 전달하고, 요청 로그에도 표시합니다. 이 프로젝트에서는 `max_tokens=1200`일 때 응답이 잘렸고, 4096으로 늘렸을 때 완성된 커밋 초안이 출력된 실제 실행 차이가 있습니다. 이를 근거로 기본값을 4096으로 정했습니다.

| 설정 | 확인한 실제 결과 |
| --- | --- |
| 기본값이 1200이었던 실행 | `응답이 토큰 한도로 잘렸습니다` 오류 |
| `--max-tokens 4096` | 커밋 제목과 본문 생성 성공 |

위 기록은 사용자가 공유한 실행 결과입니다. 두 설정을 새로 같은 입력으로 반복 비교한 실험은 아니며, 더 큰 한도가 항상 더 상세한 답을 보장한다는 뜻도 아닙니다. 사진의 평가 기준은 temperature **또는** max-tokens 변경이므로 토큰 한도 사례로 설명할 수 있습니다.

평가자가 직접 비교를 요청하면 같은 변경을 유지한 상태에서 다음을 실행합니다. 각 명령은 실제 API 요청 1회를 사용합니다.

```powershell
py -3.12 .\6-2\main.py commit --path 6-2 --temperature 0.2 --max-tokens 1200
py -3.12 .\6-2\main.py commit --path 6-2 --temperature 0.2 --max-tokens 4096
```

모델 출력은 매번 달라질 수 있으므로 1200에서 반드시 잘린다고 보장하지 않습니다. 요청 설정 로그, 종료 상태, 완성도와 불릿 수 등을 비교합니다. temperature 0.2와 0.8도 비교할 수 있지만 별도 실 API 비교 결과를 확보했다고 주장하지 않습니다. 파라미터가 요청에 반영되는 것은 통합 테스트로 확인합니다.

### 1-7. 제목 길이 및 형식 규칙을 만족하는가?

제목은 커밋과 PR 모두 `type: 설명` 형식을 검사합니다. 예를 들어 기능 추가는 `feat:`, 버그 수정은 `fix:`, 문서 수정은 `docs:`를 요청합니다. 접두사의 대소문자와 공백은 정리하지만, 누락된 유형을 임의로 추정해 붙이지는 않습니다. 접두사도 제목 길이에 포함합니다. 이는 기본 출력 규칙이며 팀별 보너스 커스터마이징은 아닙니다.

> 커밋 제목은 50자 이내를 권장하도록 프롬프트에 적고, 코드에서는 최대 72자를 강제합니다. PR 제목은 최대 80자로 제한합니다. 제목 줄바꿈을 공백으로 바꾸고, 한도를 넘으면 말줄임표를 포함해 한도 이내로 줄입니다. PR 필수 섹션과 각 섹션의 불릿은 검사 후 프로그램이 출력합니다.

50자는 권장 기준이고 72자가 커밋 제목의 강제 한도입니다. 글자 수는 Python 문자열 길이로 계산하며 토큰 수와 다릅니다. 제목을 자르는 과정에서 의미가 빠질 수 있으므로 후처리 안내를 보고 사용자가 검토해야 합니다.

## 항목 2. 설계와 구현 이유

### 2-1. Git 변경 수집과 API 호출을 왜 분리했는가?

> Git 수집은 로컬 파일 상태를 읽는 일이고 API 호출은 네트워크를 통해 응답을 받는 일이어서 실패 원인과 책임이 다릅니다. `collect_changes()`와 `call_api()`로 나누면 Git 문제와 API 문제를 구분할 수 있고, API 없이 임시 저장소로 Git 수집을 테스트할 수 있습니다. API 제공자가 바뀌어도 호출부를 중심으로 수정할 수 있습니다.

전체 동작을 연결하는 역할은 `main()`이 담당합니다. 함수를 나누되 작은 과제 규모에 맞춰 한 파일로 구성했습니다.

### 2-2. 프롬프트 구성과 출력 포맷팅을 어떻게 분리했는가?

> `make_messages()`는 AI가 무엇을 작성해야 하는지 정합니다. `parse_output()`은 응답이 올바른 JSON인지, 제목과 필요한 내용이 있는지 검사하고 길이를 정리합니다. `render_output()`은 검증된 데이터를 터미널에서 읽기 쉬운 헤더와 불릿으로 변환합니다. AI가 구분선과 섹션 형식을 매번 정확히 지키는 것에만 의존하지 않기 위해 분리했습니다.

입력의 민감정보 처리와 길이 제한은 별도의 `prepare_context()`가 담당합니다.

### 2-3. API 파라미터를 CLI 옵션으로 둔 이유는?

> 소스를 수정하지 않고 모델, 표현의 다양성, 출력 한도를 바꿔 비교하기 위해서입니다. 같은 명령과 설정을 기록하면 다른 사람도 비슷한 조건으로 실험할 수 있습니다. 이번에 토큰 한도 부족을 확인했을 때도 `--max-tokens 4096`만 붙여 다시 실행할 수 있었습니다.

설정 재현과 출력 문구의 완전한 재현은 다릅니다. 입력·모델·설정을 같게 해도 AI 응답이 항상 같지는 않습니다. 현재 코드는 모델·temperature·max_tokens를 로그에 표시합니다.

### 2-4. 오류 처리를 어떻게 구현했고 왜 그렇게 했는가?

> 예상 가능한 실패는 `AppError`로 바꾸어 `main()`에서 한국어 안내와 종료 코드 1로 처리합니다. 내부 traceback보다 사용자가 고칠 수 있는 원인을 전달하기 위해서입니다. 오류 뒤에 자동으로 반복 호출하지 않아 비용도 통제합니다.

| 상황 | 처리 및 이유 |
| --- | --- |
| 변경 없음 | 정상 안내, 코드 0, API 미호출 |
| 새 파일만 있고 미스테이징 | `git add` 안내, 파일 내용을 추측하지 않음 |
| 키 / URL / 모델 누락 | 누락된 설정을 명시, API 미호출 |
| HTTP 401 / 403 / 429 | 인증 / 권한 / 한도·잔액 안내 |
| TLS 인증서 오류 | 인증서 검증 유지, 이 PC에서 정상인 `py -3.12` 안내 |
| DNS / 연결 거부 / 타임아웃 | 원인별 네트워크 안내 |
| 토큰 한도 도달 | 잘린 응답을 성공으로 출력하지 않고 한도 조정 안내 |
| 잘못된 API 구조 / AI JSON / 필수 항목 누락 | 초안 출력 중단, 형식 오류 안내 |

서버의 오류 본문 전체나 API 키를 로그에 출력하지 않습니다. API 응답에서 잘못된 자료형이 들어오는 경우도 보완하여 traceback 대신 오류를 안내합니다.

## 항목 3. AI 파라미터와 프롬프트 이해

### 3-1. temperature를 높이거나 낮추면 어떻게 달라지는가?

> temperature는 생성할 표현을 선택할 때의 무작위성에 영향을 줍니다. 낮추면 비교적 일관되고 안정적인 표현을, 높이면 더 다양한 표현을 얻는 경향이 있습니다. 커밋과 PR은 사실에 근거한 설명이 중요해서 기본값을 0.2로 정했습니다. 낮다고 정확성이 보장되거나 높다고 무조건 더 자세해지는 것은 아닙니다.

허용 범위는 프로그램에서 0~2로 검사합니다. 실제 모델과 API의 지원 범위는 다를 수 있으므로 해당 제공자의 규격을 따라야 합니다.

### 3-2. max_tokens의 영향과 설정 근거는?

> max_tokens는 생성에 사용할 수 있는 토큰의 최대 한도입니다. 정확히 그 길이만큼 쓰라는 지시가 아닙니다. 너무 작으면 JSON이나 PR 본문이 완성되기 전에 잘릴 수 있고, 높이면 더 긴 출력을 허용하지만 사용량도 늘 수 있습니다. 토큰은 글자와 일대일 대응하지 않습니다. 모델에 따라 추론에 쓰이는 토큰도 한도에 영향을 줄 수 있으므로 실제 API 동작을 확인해야 합니다.

이번에는 1200에서 잘림 오류를 확인하고 4096에서 정상 결과를 얻어 기본값을 변경했습니다. 정확한 입력·출력 토큰 수나 추론 토큰 내역은 저장하지 않았으므로 잘림의 세부 원인을 단정하지 않습니다.

### 3-3. 목적에 맞는 결과를 위해 프롬프트에 무엇을 넣었는가?

> 시스템 메시지에는 한국어 작성, Git 변경에 근거한 설명, 제목 길이, 필요한 JSON 필드, 불명확한 의도의 추정 표시, 실행하지 않은 테스트를 실행했다고 쓰지 말라는 규칙을 넣었습니다. 사용자 메시지에는 파일 목록과 실제 diff를 넣었습니다. 커밋은 제목과 핵심 요약, PR은 배경·변경·검증 방법이 필요하므로 명령마다 응답 구조를 다르게 요청합니다.

또한 코드나 주석 속의 문장을 AI에 대한 지시로 따르지 않도록 명시합니다. 프롬프트가 모든 오류나 악의적인 입력을 막는 것은 아니므로 결과 검증과 사람의 검토도 유지합니다. 현재 변경 이유나 요구사항을 별도 옵션으로 입력받는 기능은 없으며, diff만으로 알 수 없는 배경은 사람이 보완합니다.

### 3-4. 재생성과 후처리 중 무엇을 선택했고 왜인가?

> 후처리를 선택했습니다. 제목의 줄바꿈과 길이를 정리하고, JSON 데이터를 정해진 헤더와 불릿으로 출력합니다. 이를 코드로 처리하면 규칙 적용이 일정하고 추가 API 요청이 없어 비용과 대기 시간을 줄일 수 있습니다. 명령 1회당 API는 최대 1회 호출합니다.

누락된 Why나 테스트 방법을 코드가 임의로 만들어 넣지는 않습니다. 의미 있는 내용이 없거나 JSON이 깨진 경우에는 오류로 종료합니다. 즉, 형식은 후처리하고 복구할 수 없는 내용 오류는 검증 실패로 처리하는 방식입니다.

## 항목 4. 검토, 보안, 향후 개선 판단

### 4-1. AI가 쓴 내용을 바로 사용하면 안 되는 이유는?

> AI는 diff만 보고 변경 의도를 추정하므로 실제 이유를 잘못 설명하거나 중요 변경을 빠뜨릴 수 있습니다. 실행하지 않은 테스트를 수행했다고 쓸 수도 있습니다. 특히 기본 안전 모드에서는 diff를 200줄로 제한하므로 전체 맥락이 부족할 수 있습니다. 그래서 코드 변경과 설명을 대조하고, 테스트 명령을 실제 환경에 맞게 수정한 뒤 사용해야 합니다.

이번 실제 PR 초안은 `python` 실행을 제안했지만 이 PC에서는 인증서 문제 때문에 `py -3.12`가 맞았습니다. 이는 생성된 테스트 방법도 검토해야 한다는 구체적인 사례입니다. 길이와 섹션 검사를 통과해도 사실의 정확성이 보장되는 것은 아닙니다.

### 4-2. diff의 민감정보 유출을 어떻게 막는가?

> 키는 환경변수로만 받고 `.env`는 Git 추적 대상에서 제외하도록 설정했습니다. 기본 안전 모드에서는 이메일과 일부 키 패턴, 비밀값 대입 패턴을 마스킹하고 입력량을 제한합니다. 사용 중인 API 키 자체는 안전 모드를 꺼도 입력에서 제거합니다. 전송 전에 `git diff`와 `git diff --cached`로 내용을 확인하고 `--path`로 필요한 작업 범위만 선택합니다.

현재 마스킹은 모든 토큰 형식, 개인정보, 여러 줄 비밀값을 탐지하지 못합니다. 줄 수 제한은 유출량을 줄이는 기능이지 비밀 탐지의 대체가 아닙니다. 이미 Git이 추적 중인 파일은 `.gitignore`만 추가해도 제외되지 않습니다. 이 한계를 설명하고 사람이 검토하는 절차를 유지합니다. 사용자 지정 마스킹 정책 등 보너스 고도화는 구현하지 않았습니다.

### 4-3. 실제 팀에 적용한다면 무엇을 먼저 개선하고 왜인가?

> 먼저 외부 전송 전에 실제 전송할 파일과 마스킹된 내용을 보여주고 사용자가 확인할 수 있는 기능을 추가하고 싶습니다. 팀 저장소에는 고객정보나 내부 설정이 포함될 수 있고, 유출되면 되돌리기 어렵기 때문에 문장 스타일 개선보다 먼저 다루겠습니다. 이 화면에서 생략된 diff도 알려주면 누락된 요약을 검토하기도 쉬워집니다.

이 답변은 향후 우선순위에 대한 설명이며, 해당 기능은 현재 구현하지 않았습니다. 현재는 생략 여부를 터미널 경고로 알리는 기본 보완만 했습니다. 보너스 기능을 수행했다는 의미가 아닙니다.

## 평가 시연 순서와 증빙 범위

1. `6-2`에서 `py -3.12 -m unittest -v`로 자동 검증을 보여줍니다. 테스트는 임시 Git 저장소와 모의 응답을 사용하므로 실제 API 비용이 없습니다.
2. API 키를 설정한 PowerShell 창에서 저장소 루트로 이동합니다. `git status --short -- 6-2`로 시연할 변경이 있는지 확인합니다.
3. 변경이 없다면 추적 중인 README의 설명을 실제로 개선하는 등 작은 변경을 직접 만듭니다. 다른 사람의 변경을 되돌리는 명령은 사용하지 않습니다.
4. `commit --path 6-2`와 `pr --path 6-2`를 실행하고 제목, 본문, 요청 설정, 호출 횟수 로그를 확인합니다. 캡처에 키가 포함되지 않도록 합니다.
5. 파라미터 비교가 필요하면 같은 변경에 대해 위의 1200 / 4096 명령을 실행합니다. 관찰한 결과만 기록합니다.
6. 테스트와 실제 실행 증빙을 구분하여 설명하고, 보너스는 미수행으로 안내합니다.

현재 실제 API 키는 사용자의 PowerShell 세션에서 설정했으므로 에이전트가 별도로 키를 읽거나 새 유료 요청을 수행하지 않았습니다. 사용자 제공 실행 기록이 기존 실제 API 증빙이며, 이번 보완 이후의 새 전체 터미널 캡처는 별도 실행이 필요합니다.

## 짧은 발표용 설명

> Git 변경을 Python에서 수집하고, 민감정보를 처리한 뒤 AI API로 커밋과 PR 초안을 생성했습니다. 수집·프롬프트·API 호출·결과 검증을 분리해 테스트와 유지보수를 쉽게 했습니다. 낮은 temperature로 비교적 일관된 표현을 요청하고, 실제 잘림 문제를 해결한 4096을 토큰 기본값으로 사용합니다. 제목 길이와 PR 섹션은 코드로 검증하고 후처리하며, 의미가 틀릴 수 있어 사람이 최종 검토합니다. 키 누락과 네트워크 오류는 원인별로 안내하고, 요청은 실행당 1회로 제한했습니다. 보너스 과제는 제외했습니다.
